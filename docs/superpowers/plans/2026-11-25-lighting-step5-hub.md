# Lighting Step 5 (The Hub) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** With a saved switch in Settings → Lighting turned on, DeadWare's own driver lights the Corsair iCUE LINK System Hub, reads its coolant temperature and fan and pump speeds, and hands it back on every controlled stop. With the switch off, 0.23 treats the hub exactly as 0.22 does. No fan or pump speed is ever set.

**Architecture:** A hub worker inside the helper (`DeadWare.Devices`): a single-threaded core that is stepped with the current time, wrapped by a thin dedicated thread that also owns the shared Corsair lock and a real-time watchdog. The host's loop never waits on the hub: it posts the newest colours, allows or forbids holding, and reads the worker's last snapshot. The hub is a second own device beside the mouse, under the fixed key `linkhub`. A take-over is a small state machine the host drives around one deliberate OpenRGB restart. Readings travel to the window as their own event and join monitoring as a second sensor source.

**Tech Stack:** .NET 10, C#, WinUI 3 (code-built pages), HidSharp 2.6.4 (already referenced by `DeadWare.Devices`), `System.Threading.AccessControl` (in the box), OpenRGB.NET 3.1.1, xUnit 2.9.3, `FakeTimeProvider`.

## Global Constraints

- Work only in the worktree. Never run git or dotnet in `I:\DeadWare` itself. Never launch DeadWare, the helper, OpenRGB, DeadLight or iCUE. Never tag.
- **Nothing a build or a test does may touch the hub.** No test constructs `HidHubTransport`, lists HID devices, or opens `Global\CorsairLinkReadWriteGuardMutex`; hub tests use the fakes of Task 4 and a test-only lock name.
- **No speed is ever set.** A `HubFrame` is the only thing a port can send (`IHubPort.Write(HubFrame)`, Task 4), and a `HubFrame` factory is the only way to make one (Task 3). Nothing adds a factory, an endpoint or an opcode outside that task's list; a frame's bytes cannot be changed once it is built; and the only other code in `src` that fills a 513-byte buffer is `HidHubTransport`, which copies a frame into it.
- **No device id** in a fixture, test, comment or log line. Fixtures use the synthetic 26-character ids of Task 3.
- Build: `dotnet build DeadWare.slnx -c Release` (0 errors, no new warnings). Tests: all three projects with `--filter "FullyQualifiedName!~MeasurementTests"`; both pass before every commit.
- Every new test is seen failing for its stated reason before the code that passes it, or carries mutation evidence in the report. Tests state literal expected values, never a constant shared with the code under test, and use fake time (`FakeTimeProvider`, the tests' `Clock`); a `RealTimeCap` liveness wait as in the existing tests is not a deadline.
- `HostState` and `DeviceView` grow only by optional trailing members; pipe `Version` stays 1. A reply is written before the state its request caused: never raise a state inside `Apply`, set `raise=true`.
- Requests run synchronously under the host's `gate` (`DeviceHost.cs:654`): a hub request never scans processes, never waits for the hub and never awaits.
- Nothing on the host's loop or under `gate` waits for the hub. The one wait is the hand-back of at most 1.5 s when the host stops, off the lock; everything else looks at the worker's snapshot turn by turn, for as many turns as it takes (switching off and backing out of a take-over wait this way for the worker to let go).
- No timer of 500 ms or 33 ms outside the host's own ticks (the test harness recognises the loop by those periods): new host waits are timestamps from `time.GetTimestamp()` checked on the loop.
- All hub I/O and every enter and exit of the Corsair lock happen on the worker's thread, never across an `await`.
- `KeyPressRuleTests` scans every `*.cs` in `DeadWare.Devices` and `DeadWare.Core`, comments and strings included, for substrings such as `ToAscii` and `GetKeyState` (a helper named `IdToAscii` fails). `NativeLibrary`, `GetProcAddress` and function pointers stay forbidden; a new Win32 import is `[DllImport] static extern`.
- `lighting.json`: members at their defaults are not written; an untouched 0.22.0 file is written byte for byte as before.
- The CPU pump line and Cooling Health keep their sensor: hub rows carry a hardware type `CpuPumpSpeed.Select` never accepts (Task 11 pins it).
- New Core types are `public` (Core has no `InternalsVisibleTo`). Types in Devices are `internal sealed`. Core/Devices style: terse, brace-tight, no spaces after commas. WinUI style: conventional spacing, XML doc comments.
- UI text exactly as written in this plan, British spelling; speeds with a thousands separator, temperatures with one decimal, both in the invariant culture.
- Logging: one line per event, never per frame or per reading.
- New code goes in new files; `DeviceHost.cs` only wires. No code or test is copied from OpenLinkHub, OpenRGB, liquidctl or FanControl.CorsairLink.

**Behaviour (the notes; replies are the 512 bytes after the report id):**
- Frames: `[0]=0` (report id), `[1]=0`, `[2]=1`, command from `[3]`, zero-padded to 513. Commands: firmware `02 13`; software mode `01 03 00 02`; hardware mode `01 03 00 01`; close `05 01 01 <ep>`; open `0D 01 <ep>`; read `08 01`; close colours `05 01 01 22`; open colours `0D 00 22`; colours: the payload `[n+2 low, n+2 high, 00, 00, 12, 00, R,G,B…]` (n = 3 × LEDs) cut into chunks of at most 508 bytes, the first sent as `06 00 <chunk>`, each later one as `07 00 <chunk>`. 167 LEDs fit one frame; 168 need a second. `Close` and `Open` throw `ArgumentOutOfRangeException` unless `ep is HubEndpoint.Devices or HubEndpoint.Temperatures or HubEndpoint.Speeds`: any byte casts to the enum, so the factory itself checks. `Bytes` is read-only and the array behind it is never handed out.
- Replies: `[2]` echoed opcode, `[3]` status (`00` ok, `03` wrong mode), `[4..5]` data type (`21 00` devices, `10 00` temperatures, `25 00` speeds), `[6]` count. Firmware: `[4]` major, `[5]` minor, `[6..7]` patch little-endian. The reply to a `Read()` must carry status `00` to be data: `03` there is wrong mode, any other status a failure (Task 5).
- Device list: `[6]` is the last channel; records from `[7]`, channel 1 first; a record is 8 bytes (`[+2]` type, `[+3]` model, `[+7]` id length) followed by the id; id length 0 is an empty channel. The id bytes are skipped, never kept. `Used` is the offset after the last record. A record that would run past the reply's end sets `Overflow`: every offset is bounded by `reply.Length`, which can be less than 512 (`IHubPort.Read` may return a shorter report). A reply shorter than 7 bytes is malformed.
- Values: entry *i* at `7+3i`: status (`00` available) and a 16-bit little-endian value, kept in `Raw` as signed, which is right for temperatures; a speed is the same bits read unsigned (`(ushort)Raw`), since an RPM is never negative. A count whose entries would run past the reply (`7+3*count>reply.Length`; more than 168 in a full reply) is malformed. There is no other bound: 52 and 26 are normal.
- Parts table (names and LED counts are what OpenRGB 1.0rc3 lists; kind and sensor from the notes). Fans, no coolant: `0F/00` "iCUE LINK RX RGB" 8; `01/00` "iCUE LINK QX RGB" 34; `13/00` "iCUE LINK RX" 0. **Behaviour (single-threaded: only `Step` touches the transport and the lock):**
- **Calls never wait.** The `IHub` calls only store the newest value under a small lock and call `Nudge`. `Step` copies its inputs under that small lock at its start and never holds it during I/O; `Snapshot` is a volatile field read. `LetGoAsync` only records the request: its task is completed by the next `Step`, never on the caller's thread.
- **Sending.** One exchange: read and discard waiting reports with `Read(1)` until the first null, at most 16 (HidSharp has no read that does not wait; these reads count inside the unit's time limit, and at Windows' default timer resolution an empty one can take about 16 ms); write the frame; then read (250 ms each) until a reply echoes the opcode, and for `Read()` frames also carries the endpoint's data type and status `00`; up to 16 others are skipped.
- **Locked units.** Every exchange is inside one: `if(!corsairLock.Enter(LockLimitMs)){/* a skipped round */}else try{…}finally{corsairLock.Exit();/* and BusySince back to 0 */}`, so `Exit` runs on every way out, an exception included. The units are: the take, from the firmware read to the first speeds reply, as one (seventeen exchanges under one `Enter`); the dialog's reading as one; and while held, each read transaction (close, open, read, close of one endpoint), each colour transaction (close colours, open colours, the chunks, close colours) and a mode command alone. `Enter` false is a skipped round, not a failure, at the start of the take and of the dialog's reading too (the port opened for it is closed again); it is logged once per spell (`Corsair lock busy`, then `Corsair lock free again`). A missing or malformed reply, a `Read()` reply whose status is neither `00` nor `03`, an exception from the port, **any other exception inside a unit**, or a unit past its limit on the core's clock (1.5 s; 2 s for the dialog's reading) is a failure. No exception leaves `Step`.
- **Take** (when allowed, not quiet, not held, not on hold, past the retry time), logging `hub: take started`: `Count()` 0 → let go `noHub`, more than 1 → `twoHubs` (both hold until `Recheck`); a lock `Problem` → `noLock` (holds for the run); `Open`; then, as one locked unit: firmware (`hub firmware 4.1.656`); probe: close, open, close of `Temperatures`, logging `hub was in its own mode` when the open answered `03` (expected there, not a failure), else `hub was still held`; software mode (`hub: software mode entered`; `SoftwareAt` = now); device list → `HubParts.Build`; a blocker → hardware mode, close, let go with it (`hub unsupported: <phrase>`), hold until `Resume` or until a `Recheck` finds the hub after it was missing; each part logged as `hub part: channel 13, type 0x11, model 0x02, 20 LEDs`; temperatures and speeds once. The core counts as holding the hub from the moment software mode is sent, not from the `driving` snapshot: a forbid or a `LetGoAsync` that arrived during the take is acted on by the next step and sends hardware mode. After the first `Count()` of a run, a result that changes between 0, 1 and more than 1 is logged once per change: `hub appeared`, `hub disappeared`, `more than one hub listed`.
- **While held**, in this order each step: readings every 3 s (temperatures, then speeds; `ReadingsAt` = now; a part whose reading appears or disappears is logged once, values never); a colour frame when the colours or dark changed and at least 125 ms passed since the last colour write, or when 2 s passed since it.
