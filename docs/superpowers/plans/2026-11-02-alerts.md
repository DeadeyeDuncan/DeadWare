# Alerts Implementation Plan (0.8.0)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Execute inline under the user's standing preference.

**Goal:** Let the user define threshold rules over the metrics DeadWare already records, notify once per episode from the tray, log every episode locally, and show the evidence in Usage history.

**Architecture:** A pure core evaluator consumes the usage folder's closed minutes and battery readings and emits episode start and end events. A background alert service owns the evaluator, the day accumulator for application budgets, the mute switch and tray notifications, and writes episodes to a new bounded SQLite log. An Alerts page edits rules stored in settings, shows recorded statistics beside each threshold, lists episodes, and hands off to Usage history.

**Tech Stack:** Existing .NET 10, WPF, Microsoft.Data.Sqlite, xUnit and the Windows Forms tray icon. No new package dependencies.

**Spec:** `docs/superpowers/specs/2026-11-02-alerts-design.md`

## Global Constraints

- Alerts evaluate recorded minute averages and battery readings only; nothing is added to the collector's publication path and no new sensors are polled.
- One notification per episode, re-armed by hysteresis, never more than one per rule per hour; application budgets once per local day. Every episode is logged whether or not notifications are on.
- Rules are user-set; suggestions are recorded statistics and never change a threshold by themselves.
- The log store follows the other stores: bounded background writer, 15-second flush, Quit drain within the history deadline, sign-out path, failure reported without stopping monitoring.
- Cooling Health's warnings, references and notification setting are untouched.

## Review Focus

- A sample gap must reset a duration count; an unavailable reading must neither count nor reset (Task 1).
- Local-day boundaries for application budgets, including the DST transition, must not double count or skip a day (Tasks 1/3).
- A rule edited mid-episode must end the old episode cleanly and start fresh (Tasks 1/3).
- Notification failures must never turn a logged episode into a service failure (Task 3).
- The Usage history hand-off must land on the Day containing the episode in local time (Task 4).
