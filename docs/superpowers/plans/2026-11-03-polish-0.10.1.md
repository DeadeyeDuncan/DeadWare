Files: `src/DeadWare.App/Charts.cs` (~line 267), `tests/DeadWare.App.Tests/LiveRenderingUiChecks.cs`.

- Delete the line `if(showRpm)left=Enumerable.Range(0,3).Max(i=>Formatted(FanAxis(fanMaximum*i/2)).Width)+10;` so `left` stays `compact?3:8` whether or not a GPU fan / CPU pump overlay is shown. `ChartFrame.Grid` already draws the `leftLabels` RPM labels inside the plot (left-aligned) since 0.9.0, so the margin is dead space.

## Task 2: Per-core minors deferred from 0.10.0

Files: `src/DeadWare.App/Collector.cs`, `src/DeadWare.App/CpuCoreUsage.cs`, `src/DeadWare.App/ThemeTokens.cs`, `src/DeadWare.App/GraphHistoryService.cs`, matching tests.

2a. **Hold the last good core count for one poll.** In `Collector.cs` around line 155: when `CpuCoreUsage.FromSensors` returns empty and `hardwareCores` is true (hardware previously reported cores), re-publish the previous poll's core list with `null` values once (so `CpuCoreCount` stays and the trace shows a gap, not a disappearance); a second consecutive empty poll publishes an empty list as today. Keep a private field for the last good count; reset on a non-empty read. Test in `CollectorPollingTests.cs` via the static helper pattern if feasible (add a small `internal static` pure function, e.g. `HoldCores(IReadOnlyList<double?> read,ref int held,bool hardware)`, and test it directly: non-empty → returns read, held=count; empty with held>0 → returns count nulls, held=0; empty with held==0 → empty).

2b. **Notice when more than 64 cores are dropped.** `CpuCoreUsage.FromSensors` truncates silently at `MaximumCores`. Add an `out int dropped` overload (keep the existing signature delegating to it). In `Collector.cs`, when `dropped>0`, append ` · Showing the first 64 of {64+dropped} CPU cores.` to `hardwareStatus` (same pattern as the GPU/CPU-temperature notices on lines 170-171). Test: extend `CpuCoreUsageTests.More_than_sixty_four_entries_are_capped` to assert `dropped` equals the excess.

2c. **Smooth the tint saturation cliff.** `ThemeTokens.CoreTint` line 38: `s<0.25?Math.Max(s*0.85,0.7):s*0.85` jumps from ~0.21 to 0.70 at s=0.25. Replace with a continuous blend: for `s<0.25`, `lerp(0.7, 0.25*0.85, s/0.25)` (so s=0 → 0.7, s=0.25 → 0.2125, matching the s≥0.25 branch). Existing `ThemeTokenTests` must still pass (64 distinct tints for the near-grey set). Add one test asserting tints at s=0.249 and s=0.251 differ by less than, say, 8 per channel for the same index/count.

2d. **Restore-fill chaining.** In `GraphHistoryService.cs` ~lines 88-103, `lastBySession` is updated from `values` after filling, so a filled record becomes the next fill source and a single real core record propagates through an unbounded chain of thinned records within `fillWindow` steps. Change it so `lastBySession` records the cores from the *record's own* values (before fill) and only advances the stamp when the record itself carried core keys. Existing tests `Restored_core_history_fills_cadence_thinned_records_without_gaps` and `Restore_does_not_fill_cores_across_a_gap_longer_than_the_cadence` must still pass; add a test: one core record, then four records 0.5 s apart without cores at 64-core cadence (2 s), then confirm records more than `fillWindow` after the real core record have no core key.

If any sub-item turns out to need a design decision (e.g. 2d breaks the continuity test for a reason the spec supports), skip it, leave the code untouched, and say so in the report under "deferred".
