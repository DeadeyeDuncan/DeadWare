## Application resource history (0.14.0, 2026-11-06)

### One-day size

`One_day_at_the_cap_stays_under_four_mebibytes` (`tests/DeadWare.Tests/ProcessHistoryStoreTests.cs`) writes one day at the cap, 1,440 complete minutes with the same 30 app names plus Everything else and full-width counter values each minute, and asserts the files stay under 4 MiB. It passed with `dotnet test tests/DeadWare.Tests -c Release -p:EnableWindowsTargeting=true --nologo --filter "FullyQualifiedName~One_day_at_the_cap"` on Linux on 2026-11-06. A throwaway copy of the test that printed `StorageBytes` (not committed) measured:

- 2,740,224 bytes (2.61 MiB) with the test's one-character machine key;
- 3,522,560 bytes (3.36 MiB) with a 15-character key, the longest computer name `Environment.MachineName` returns on Windows. The app keys rows by that name and stores it in every row.

Worst case: a busy day near the cap is about 3–4 MiB, so 30 days plus today (31 × 3.4 MiB, about 104 MiB) fit under the 128 MiB cap (`ProcessHistoryStore.MaximumDatabaseBytes`, `RetentionDays` 30). The spec's estimate of about 2 MB per day was low. Whole-day eviction bounds the file whatever real days hold.

### Behaviour the release notes describe

- Recording has no switch of its own: `ProcessHistoryService` records while `UserSettings.ProcessMonitoring` and `UserSettings.UsageRecording` are both on. Turning either off keeps the saved file, and its days still leave once they are 30 days old.
- Retention has one cutoff, `ProcessHistoryStore.RetentionCutoff(now)`: the UTC day floor of now minus 30 days. `Expire(now)` deletes every older minute and its app rows for every machine, one UTC day per committed transaction with a checkpoint between days; `Append` runs the same step before its insert transaction. The service's worker, which runs whether or not it records, calls `Expire` right after initialization and on the flush tick whenever the UTC day has changed. `ReadApplications`, `ReadSeries` and the earliest retained minute never reach before the cutoff, even before expiry has run.
- Each minute keeps the union of the top 10 apps by CPU time, by memory and by I/O read + write (at most 30) plus one Everything else row holding the rest of the apps the scan saw. Activities with monitoring off add nothing, so those minutes are gaps, not empty rows.
- Usage by processes that exit between scans is not recorded: `ProcessActivityTracker` credits a process only up to the last scan that saw it, so a process that starts and exits between two scans, and a process's last moments before it exits, are in no row. Saved totals can be lower than the Device charts.
- CPU time and I/O are stored as whole numbers that are never unknown, so an unknown delta inside a valid scan interval (an app's counters went backwards, or a process that started earlier was seen without a baseline) folds as 0: a stored minute can understate rather than be marked unknown.
- A minute is saved after it closes, at the next 15-second flush; the card's gap count leaves out a minute that has just ended until it has had time to arrive, and counts only from the retention cutoff. A period that starts before the cutoff says "Application resources are kept for 30 days; earlier minutes are not kept.", in place of "No application resources were recorded in this period." when the whole period is older.
- A restart inside a minute keeps the first segment's rows and clears `complete`; a dropped or skipped publication marks the open minute incomplete, and when the next activity starts a new minute that minute is marked too (the old one may have lost its tail, the new one its head). A crash after a recording switch, before the next resume or Quit, loses the open minute.
- The Application resources table lists up to 200 apps for the period (`ReadApplications`' default limit) plus Everything else. The same read counts every application in the range (`ApplicationCount`), so past the limit the summary says "Top 200 of N applications · …" and a search says "N of the top 200 applications match.".
- The card's status line follows Record usage history and Per-process monitoring as they change (`RefreshStatus`, no database read). The selected app's series is read with the CPU chart's point count, capped at 1,000, so its buckets are the Device charts' slots, and its CPU labels keep one decimal under 10 %. The CPU and RAM charts draw an Accent frame while they have keyboard focus, and Clear hands its focus to the chart that listed the slot, or to Rank by.
- Click a moment lists the clicked bucket's own slot (the CPU and RAM charts share `ReadMetric`'s grid), ranked by CPU time from the CPU chart and by average memory from the RAM chart. Clear and Esc return to the period ranking; changing the range, **◀ Earlier**, **Later ▶** and an alert's **View in Usage history** clear the slot, and the page's minute refresh keeps and re-reads it.

## Processes (0.13.0, 2026-11-06)

### Measurements and decisions

Measured on GitHub `windows-latest`, elevated, in CI run https://github.com/DeadeyeDuncan/DeadWare/actions/runs/42148708989 (head `e1b0af5`), recorded by the real-Windows measurement tests.

Process scan (`scan-timing.json`): 240 scans, p50 0.478 ms, p95 0.526 ms, initial buffer 1,048,576 bytes, 147 processes and 1,543 threads, 0 failures.

Disk attribution (`disk-attribution.json`): the run stopped at the first loss-free buffer size, so one size was measured. At `BufferSizeMB` 64 the session was running and unpaused, the test's own `(Pid, Generation)` was credited 1.0051 of the 256 MB unbuffered write-through file, the unattributed share was 0, no events were lost and the longest lossy run was 0. The chosen size is 64 MB and the loss limit was not hit.

A share slightly above 1.0 is expected; the likely cause is that NTFS metadata writes are credited to the writing process on top of the file data.

Decisions (spec, Recording the decisions):

- `ProcessFeatures.ScanLoop = false`: p95 0.526 ms is at or below 15 ms, so the scan runs on every poll and no separate loop is needed.
- `ProcessFeatures.DiskBufferMultiplier = 1`: the chosen 64 MB equals `EtwDisk.DefaultBufferSizeMB` (`max(64, 2 x cores)`, 64 on the 4-core runner), so the default buffer is kept.
- `ProcessFeatures.DiskColumns = true`: the run was elevated and the share 1.0051 is at least 0.90 at the chosen size, so the Disk columns ship in 0.13.0 (not 0.13.1). The gate test now enforces the 0.90 share in CI.

## Reliable tests and manual releases (0.7.1, 2026-11-02)

Five timing-sensitive App tests failed intermittently across the day's CI runs (two cooling shutdown tests, the graph periodic flush, a connection clock-rollback flush and a session-ending drain) while the suite was otherwise green, costing re-runs and two release attempts. The common mechanism was thread-pool starvation: xUnit runs classes in parallel, a dozen service tests deliberately park a pool thread inside a worker callback, and a four-core runner injects replacement threads at about one per half second, so continuations behind one-second and five-second deadlines in other classes waited for thread injection. The test host now raises the pool minimum to 64 at module load and runs the ten service, shutdown, capture, geolocation, download and update classes in one non-parallel collection; a UI check also drains fire-and-forget settings saves before deleting its directory. No production code changed. Evidence is the green CI runs since the change; the claim is reliability under runner load, not a change in app behavior.

The Release workflow gained a manual trigger that creates (or, after a failed run, moves) the version tag with the workflow token and then publishes as a tag push does; v0.7.0 was published this way after three attempts, the first two stopped by the tests above. The remaining 0.7.1 checklist items from the alerts plan (real-machine soak, database growth measurement and the Year/All decision, High Contrast and 150% DPI renders, the Save dialog) still need a Windows machine and are not claimed by this release.

## Disk graph history and drive line colours (0.12.5)

Reported symptom: after a restart, the widget's Disk graph showed only a thin red line for the restored part and the blue read and green write lines began at the restart. Root cause: `GraphHistoryProjection.Mappings` persisted each persistable drive's `storage/<id>/read|write` but not `storage/total/read|write`, which drive the Disk graph's read and write traces, so the restore had nothing to put under them. The thin line was a per-drive trace, drawn with `Theme.CoreBrush`, a tint of the CPU colour that also honoured `cpucore/N` overrides.

## Energy saver in battery history (0.12.4)

Reported symptom: with Windows Energy saver on while discharging, the Battery history charge line never turned amber. Root cause: DeadWare read saver state only from `GetSystemPowerStatus` → `SYSTEM_POWER_STATUS.SystemStatusFlag`. On Windows 11 24H2 and later, Energy saver replaced battery saver and has two active levels, Standard and High savings. The legacy flag (and its `GUID_POWER_SAVING_STATUS` notification) reports on only for High savings, so Standard periods were stored as a known saver=0 and drawn in the normal colour. Evidence: Microsoft's merged Windows App SDK `EnergySaverStatus2` spec maps Standard → legacy Off and High savings → On; the Windows SDK `winnt.h` (10.0.26100 and later) marks `GUID_POWER_SAVING_STATUS` deprecated in Germanium in favour of `GUID_ENERGY_SAVER_STATUS` (0 off, 1 standard, 2 high savings); two independent projects measured `SystemStatusFlag` = 0 with Energy saver on. The struct layout and the 0/1 mapping were correct. A port of the recorder, the SQLite bucketing and the chart (cross-checked against the repo's own tests and real SQLite) draws an amber Day line in every simulated case once saver=1 is recorded, so the chart was not at fault; Week and longer ranges show amber dots and marks rather than a line by design.

Fix: `EnergySaverStatus` registers once per process, unelevated, for `GUID_ENERGY_SAVER_STATUS` through `powrprof!PowerSettingRegisterNotification` with `DEVICE_NOTIFY_CALLBACK`; Windows calls back immediately with the current level and on every change, and the callback reads the DWORD at offset 20 of `POWERBROADCAST_SETTING` into a volatile field. `BatteryReading.FromWindows` treats Standard or High savings as saver on and otherwise honours the legacy flag; with no reported level (older Windows, or a failed registration) the legacy flag decides alone, as before. The stored schema is unchanged; history recorded before 0.12.4 keeps its saved state.

Also in this release: the overview preview tool asserted exactly seven charts, but since 0.12.1 the sample storage's two drives add two drive cards, so `--render` threw on every build. The CI "Render previews" step ran both renders in one `pwsh` block that reports only the last exit code, which masked the failure. The assert now expects seven plus one per sample drive, and the step checks `$LASTEXITCODE` after each render.

Automated (authored without a .NET SDK; the pull request's Windows CI builds and runs both test projects): `Energy_saver_level_decides_saver_where_the_legacy_flag_stays_off`, `Without_an_energy_saver_level_the_legacy_flag_decides_alone` and `Energy_saver_setting_is_read_from_its_own_guid_and_dword` in `BatteryHistoryTests`; `WindowsBatteryTests` reads a native `POWERBROADCAST_SETTING` built in unmanaged memory through `ReadSetting`, the callback's parser (`OnChange` and the native thunk run only when Windows calls back), and checks that reading the battery twice makes exactly one registration attempt without throwing. A review pass found that the first poll after launch read the level before Windows' initial callback arrived, so each launch recorded a false one-second "off"; registration now waits up to 250 ms, once, for that first report.

Pending until checked on a physical Windows 11 24H2+ laptop: switch Energy saver on while on battery above 20 %, and within a minute the Day line turns amber and the Saver marks fill; switch it off and the line returns to the normal colour; with "Always use energy saver" while plugged in the line is amber too. On Windows 10 or 11 23H2 and earlier, battery saver still shows amber.
