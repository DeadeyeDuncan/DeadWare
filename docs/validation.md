## Persistent live graphs candidate (0.4.2)

The Release solution build and all 194 automated tests passed (168 core, 26 Windows app). New tests cover SQLite close/reopen, exact timestamps and zero/null values, six-hour/count/size boundaries, idempotent writes, malformed/corrupt/newer caches, lock timeout and actual SQLITE_FULL transaction rollback. Runtime tests cover restart rebasing without overwriting live values, delayed hardware discovery, unique GPU enumeration changes versus replacements/ambiguous devices, machine isolation, periodic flush without another publication, clock discontinuities, bounded queue loss, and final graph-cache draining while a hardware provider remains stuck. The existing three-second Windows session-ending deadline remains in place.

Independent review found an overflow boundary could be applied to an earlier queued sample. The fix captures the loss generation with each accepted queue item; a deterministic 120-queued / 121-dropped / 122-accepted regression verifies the saved session split and restored graph break. Future, expired and nonfinite rejected publications also split the next persisted segment; duplicate monotonic publications do not. Follow-up review found no remaining high or medium severity issues.

Graph data is stored separately in `live-graph-history.db`, with no new dependencies or collector. Only CPU/GPU usage and temperature plus aggregate download/upload values are persisted under hashed local device identities. Sensor-table statistics and application traffic details remain session-only. The graph cache preserves six elapsed hours, not six accumulated hours of uptime; downtime is a gap. A sudden termination can lose the unflushed batch. Same-model physical replacement cannot always be distinguished; ambiguous identical GPUs are skipped. Previous versions ignore the new cache, and the first upgrade cannot recover their unsaved memory-only traces.

A separate isolated SQLite/offscreen WPF probe passed 32 assertions on the built application controls. Midnight/Daylight compact and wide CPU/network graphs remained legible, and normal/long storage-error status text fit the dashboard's 900-pixel minimum. The cache used 18,812,928 bytes; loading took about 317 ms, direct merge 52 ms, and the actual background service's load/map/restore/flush/stop about 470 ms. Bulk fixture creation took 3.41 seconds; offscreen rendering averaged approximately 7-16 ms. These local synthetic measurements do not prove a physical reboot, native popup interaction or a live six-hour soak.
