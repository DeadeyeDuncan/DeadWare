## Features

- CPU and GPU utilization and temperature graphs with detected device names, drawn as smooth curves on a hairline grid with wall-clock time ticks and a hover readout of the time and values at any sample.
- Optional GPU fan RPM on temperature graphs, with a separate scale and saved history.
- Optional CPU pump RPM on CPU temperature graphs, with its own setting, the same left RPM scale and saved history.
- Optional per-core CPU usage: thin lines under the bold total on the usage graphs, with a hover list of the busiest cores.
- Drive monitoring: a Disk card with total and per-drive read/write throughput, a Storage page with temperature, health, wear and free space per volume, an optional widget Disk graph, a six-hour per-drive history (up to 8 drives) and drive temperatures as Storage devices in Cooling Health. Temperature and health come from the **Storage sensors** switch (on by default).
- A combined download/upload graph with a shared scale and distinct line styles.
- Per-application network rates when Windows permits ETW capture.
- Processes: CPU, memory and I/O per app for every user, plus physical Disk and Network per app as administrator, with expandable processes, a column picker, **End task…** and **Open file location**. Per-process monitoring is off by default.
- Connections: a filled native globe or 2D map with glowing traffic arcs, moving dots on busy routes and hover chips, a visible-node list and connection detail boxes, local saved history and an optional live widget map.
- Searchable sensor readings with minimum, maximum and average values.
- Selectable graphics adapters on multi-GPU systems.
- Separate or joined CPU/GPU graph windows and a compact widget with usage, temperature, RAM and network charts and always-on-top controls.
- Compact pop-out graphs prioritize the current reading and chart; their options menu holds history range, Always on top and sensor statistics.
- Close the dashboard to the system tray and keep graphs, the widget and monitoring running independently.
- Restore the graphs and widget left open, including their saved positions and sizes.
- Optional administrator startup at your Windows sign-in, available only from a protected folder such as `C:\Program Files\DeadWare`.
- Shared 1-, 5- and 15-minute plus 1-, 3- and 6-hour graph ranges; all windows use one collector. Choose a range from the segmented control in the dashboard header or in a pop-out's **⋯** menu. The control follows the selected app theme, and its selected range stays synchronized across windows. The choice and recent CPU/GPU/RAM/network traces are saved locally across quits and computer restarts. Cooling Health's longer saved history is separate. At 1–6 hours, a per-pixel average line shows the trend and a faint min/max band retains spikes and variation. Missing readings remain gaps, and displayed statistics use the actual readings. Short ranges retain their detailed traces. In **Settings**, turn **Smooth long-range graphs (1, 3 and 6 hours)** off to use raw traces across the dashboard, pop-outs and widget. The choice is saved; raw traces retain observed peaks and gaps without the average/range band.
- Local Cooling Health history, fixed reference comparisons, CSV export and optional sustained-change warnings. With **Extended sensors** on, CPU fan speed comes from a labeled pump or CPU Fan header.
- Lifetime battery-percentage history with recorded charging and Windows energy saver (battery saver) periods, Day/Week/Month/Year/All views, CSV export and a separate remembered window.
- Usage history: Day/Week/Month views of CPU and GPU usage and temperature, RAM and network, per-application download/upload totals, CSV exports and a separate remembered window, kept for up to 400 days. With Per-process monitoring on, **Application resources** ranks the busiest apps' CPU, memory and I/O, kept for 30 days, and clicking a CPU or RAM point lists that moment's busiest apps.
- Alerts: your own thresholds on CPU, GPU, RAM, network rate, an application's daily traffic or battery charge, with tray notifications, a 400-day log and a jump to the Usage history minutes behind each alert.
- Startup and manual GitHub release checks, update-available notices, verified user-initiated updates and rollback to the previous installed version.
- Update downloads clean up after themselves, and installations in a protected folder update through an administrator-only update folder.
- Nine saved themes: **Midnight**, **Ember**, **Glacier**, **Amethyst**, **Neon**, **Blackout**, **Skyrim**, **Mage**, and **Daylight**. Open the sidebar's **Color theme** menu and hover over **Elder Scrolls Themes** to choose **Skyrim** (charcoal, silver and frost blue) or **Mage** (violet, arcane cyan and antique gold). Both add readable Nordic lettering, subtle stone surfaces and runes along live graph traces while keeping numeric readings clear. Use arrow keys and Enter to navigate the menu with a keyboard. Custom graph colors remain in effect when switching themes.
- Scrollbars follow the selected theme across all windows, with matching native title bars on Windows 11.
- Themes coordinate text colors and fonts across headings, controls, tables, graph labels and tooltips, and update open windows immediately.
- See-through glass windows: choose **Settings → Window glass** (**Off**, **Subtle**, **Balanced** or **Strong**) to let the blurred desktop show through the dashboard, pop-outs and widget behind palette-tinted panels with highlighted edges. Requires Windows 11 22H2 or later; the focused window shows the glass and unfocused windows use the solid theme surface. **Off** keeps solid glass-style panels. Blackout keeps pure-black backgrounds and panels; Windows High Contrast and disabled Windows transparency use solid surfaces. Panels are cards with hairline borders, the sidebar uses vector icons with an accent bar on the current page, the page header is one toolbar row with a hardware subtitle, and Settings groups its options into cards.
- Use the filled circles in each Overview graph's corner to choose its line color, **Default / Solid / Dashed / Dotted** pattern, **Line thickness** (50–300%) and optional **Neon glow** with **Glow strength** (0–300%). 100% preserves the original thickness/glow. Choices are saved and shared with pop-outs, widget traces and legends; download and upload have separate colors. Choose **Theme default** to clear a custom color; choose **Default** under Line style, return both sliders to 100%, and turn off glow to restore the original trace style.

## Download and run

Get the Windows x64 ZIP from the [latest release](https://github.com/DeadeyeDuncan/DeadWare/releases/latest) or browse [all releases](https://github.com/DeadeyeDuncan/DeadWare/releases). Extract the **entire** archive and run `DeadWare.exe` inside the `DeadWare` folder. The .NET runtime is bundled. The app is portable and unsigned. Version 0.6.0 adds manual update and rollback controls; older installations need one complete ZIP upgrade to gain those controls.

Windows 10/11 x64 is the target. ARM64 and other operating systems are not validated. Hardware coverage varies by device.

Start as a normal user. If a capability needs additional permissions, the app shows its status and provides an explicit administrator restart action. Administrator access does not guarantee every sensor is available. DeadWare does not disable Windows protections or install a custom monitoring driver.

## Updates and rollback

DeadWare checks the latest normal release in `DeadeyeDuncan/DeadWare` once after starting, without delaying monitoring. When a newer version is available, a dashboard banner appears outside the Updates page and a system-tray notification lets you know; **Review update** opens Updates. You choose when to download and install it with **Update & restart**. You can also choose **Check for updates** on that page at any time. Checks do not download app packages or install anything. Draft/preview releases and source commits are excluded, and an installed newer build stays on its current version. Offline or rate-limit errors appear on Updates without interrupting startup. There is no recurring polling while the app remains open.

Release notes include every normal release newer than the installed version through the offered update, newest first, with separate version headings. If earlier notes cannot be loaded, the page keeps the latest notes and explains the missing history. Installation still uses the latest eligible package.

Choose **Show release note history** in Updates to browse all normal published versions, including the installed version and older releases, newest first. Each explicit opening refreshes the history from GitHub; it is not fetched at startup. **Hide release note history** returns to the usual current or missed-version notes. Loading can be cancelled, and a failed history request can be retried without changing the offered update.

When an eligible update is available, **Update & restart** downloads the complete Windows x64 ZIP, checks its SHA-256 digest/checksum and validates the package's file manifest. Download/preparation can be cancelled. Once the installer is ready, DeadWare performs its normal Quit to save settings and drain history, replaces only managed app files, and restarts at the same path with remembered windows. Settings and battery/Cooling Health/live graph databases stay in `%LOCALAPPDATA%\DeadWare`.

**Roll back & restart** restores the previous verified installed version, keeping current settings and recordings. The first updater-enabled installation may have no registered rollback; one becomes available after an in-app update. Only a verified older backup is offered. If replacement or startup fails, the helper restores the previous app when the failed process has exited. It never forcibly terminates monitoring or overwrites a still-running replacement. A running app that did not confirm startup must be quit normally before rollback/recovery can proceed.

Updates require the complete packaged app directory, including `deadware-package.json` and `DeadWare.Updater.exe`, and permission to write app files. Shortcuts and Windows startup keep their existing executable path. Verification failures, offline checks and unavailable backups leave the current installation intact. Update checks/downloads contact GitHub and do not upload monitoring data. Update staging, the previous snapshot and operation results are stored in an `updates` directory partitioned by installation path: `%LOCALAPPDATA%\DeadWare\updates` for copies in user folders, and the administrator-only `%ProgramData%\DeadWare\updates` for an installation in a protected folder such as `C:\Program Files\DeadWare`, so programs without administrator rights can't change a downloaded update. Updating a protected installation needs **Restart as administrator**, and rolling back to a version older than 0.6.39 isn't available for it.

If an installed app file or the saved rollback copy has been changed or damaged, Updates shows a message and disables installing until you reinstall the complete package. Opening Updates also cleans up old downloads: only small records of the latest update are kept (its downloaded ZIP and unpacked copy are removed), and abandoned update folders older than a day are deleted. For an installation in a protected folder, this cleanup happens when DeadWare runs as administrator. Update data that an earlier version left for such an installation in `%LOCALAPPDATA%\DeadWare\updates` isn't cleaned up automatically; you can delete it while DeadWare is quit.

New tagged versions are published as normal GitHub releases with ZIP/checksum assets. Older historical previews remain archived and are ignored by the updater. Publishing a release is separate from pushing source to a branch or opening a pull request.

## Startup and saved workspace

In **Settings → Data polling interval**, choose 0.5, 1, 2, 5 or 10 seconds. One second is the default. Changes are saved and apply after the current wait or reading finishes, without restarting. Faster polling uses more resources; slow hardware may take longer than requested. Every window shares this collector, and the display refreshes twice per second at the fastest setting. The six-hour graph range is retained. Cooling Health records at every setting, but 5- and 10-second polling has too few samples per minute for its reference comparisons.

In **Settings**, enable **Start with Windows** to launch DeadWare as administrator when you sign in. Windows approval is needed to configure this option. It creates a task for your Windows account, runs only in your signed-in session, and stores no password. You can turn it off from the same page. Only one monitoring instance runs at a time.

DeadWare must be in a folder standard users can't change, such as `C:\Program Files\DeadWare`, to start as administrator at sign-in. A copy in a user folder (for example `AppData\Local\Programs` or Downloads) can't turn this on, and Settings explains why. If startup was already on from such a folder, Settings shows a warning: copy or extract DeadWare into `C:\Program Files\DeadWare` with administrator approval, start DeadWare from that copy, then choose **Enable / repair startup**, or turn startup off. Startup is never turned off automatically.

For a quiet sign-in, also enable **Start in the system tray**. This hides the dashboard only for Windows startup launches. Remembered graphs and the widget still reopen when restoration is enabled; turn restoration off too if you want only the tray icon. A fresh manual launch still shows the dashboard. If the tray icon cannot be created, the dashboard stays accessible.

Closing the dashboard with its X or Alt+F4 hides it in the system tray. Pop-out graphs, the widget and monitoring keep running, even with no dashboard open. Double-click the DeadWare tray icon or right-click it and choose **Show dashboard** to reopen it. Windows may place the icon in the hidden-icons area next to the clock.

To fully stop monitoring, choose **Quit DeadWare** from the tray menu or dashboard. Keep window restoration enabled and leave your desired graphs and widget open when you quit: they will reopen with their saved positions, sizes and always-on-top choices. Closing a graph or widget individually keeps it closed next time. Positions are kept within available monitors if your display setup changes. Recent graph history and saved Cooling Health history remain available after quitting. Hiding the dashboard resets neither.

Graph history is saved automatically in `%LOCALAPPDATA%\DeadWare\live-graph-history.db`, independently of Cooling Health recording. It retains the last six elapsed hours of CPU/GPU usage and temperature, GPU fan and CPU pump RPM, RAM usage percentage and combined download/upload rates. RAM uses a 0–100% scale with current used/total memory shown beside it; its history begins with readings collected in version 0.6.11 or later. GPU fan history begins with readings collected in version 0.6.20 or later; earlier samples remain unavailable. Time while DeadWare was stopped remains a gap; after more than six hours away, the old readings fall outside the available range. Current values always come from fresh readings. Writes run in the background every 15 seconds and flush on normal quit; a crash or abrupt power loss can lose the latest unsaved batch. The database is capped at 64 MiB with a bounded journal. A save error is shown in the dashboard status while live monitoring continues.

Restoration matches local machine and hardware metadata, including GPU model/type rather than enumeration order. Ambiguous identical-model GPUs are not restored; an indistinguishable same-model physical replacement cannot always be detected. Full sensor-table statistics and the Network page's per-application traffic totals remain current-session data. Connections has its own optional saved endpoint history, described below. The first upgrade from a version without graph persistence cannot recover its earlier in-memory traces.

Version 0.1.0 saved window positions but did not record which windows were open. After upgrading, arrange your desired windows once to establish the saved workspace.

Startup points to the executable's current location. Keep the extracted folder in a permanent location. If you relocate it, start DeadWare from the new location and enable startup again there. To put it in a protected folder such as `C:\Program Files\DeadWare`, copy or extract it with administrator approval instead of moving it with Explorer on the same drive, which keeps your account as the folder's owner. Disable startup before removing the app. Choose **Quit DeadWare** before replacing files during an upgrade; closing the dashboard alone leaves it running.

## Graph pop-outs

Use the overview cards' **Pop out** buttons to open graphs. In **Settings → Graph pop-outs**, enable **Join CPU and GPU graphs in pop-outs** to put CPU and selected-GPU usage together on one chart, and both temperatures together on another. The option is off by default. CPU keeps its theme color and solid line in both charts; GPU keeps its own color and dashed line. Both current readings and device statistics are available, with a shared 0–100% usage scale and a shared temperature scale that expands above 100°C when needed.

The choice applies to new pop-outs. Existing open windows and remembered layouts keep their current form, and joined and separate windows remember their own positions, sizes and pin choices. RAM, Network and Battery history windows keep their existing behavior. Open the widget from the dashboard's **Open widget** button.

In **Settings**, enable **Show GPU fan speed on temperature graphs** to add the selected GPU's first reported fan RPM to the dashboard GPU temperature graph, separate or joined GPU temperature pop-outs, and the widget temperature graph. This saved option is off by default and applies immediately to open graphs. Fan speed uses a dotted line in the theme's warning color (amber by default) and a separate left RPM scale; temperature keeps the right °C scale. A missing fan reading stays unavailable and leaves a gap. A reported 0 RPM is a valid stopped-fan reading.

Enable **Show CPU pump speed on CPU temperature graphs** to add the CPU cooler's pump RPM to the dashboard CPU temperature graph, the CPU temperature pop-out and the widget temperature graph. The joined CPU / GPU temperature pop-out keeps only the GPU fan. DeadWare reads a motherboard or AIO header labeled as a pump (for example `Pump Fan` or `AIO Pump`), otherwise the `CPU Fan` header; unlabeled headers such as `Fan #2` are not used. This needs **Extended sensors** and a single CPU. The option is off by default and separate from the GPU fan option. The pump uses a dotted line in the theme's download color (blue by default) on the left RPM scale; when the widget shows both, the GPU fan and pump share that scale. Change its color and line style with the CPU pump color button on the overview's CPU temperature card.

Enable **Show per-core CPU usage on usage graphs** (Settings, Monitoring) to draw one thin solid line per core under the bold total on the dashboard CPU usage card, the separate CPU usage pop-out and the widget Usage graph. Each line is tinted from the CPU graph colour and has no fill, glow or min/max band; on the 1–6 hour ranges the lines follow the smoothing setting as average lines. Hover a graph to see the eight busiest cores (`Core n · v%`) followed by `+N more`. A line is one LibreHardwareMonitor load sensor (`CPU Core #k`, `P-Core #k`, `E-Core #k`); where the chip exposes threads, each thread is a line, so SMT and hybrid chips show logical processors. Labels are positional (`Core 1…N`) and up to 64 lines are drawn. If LibreHardwareMonitor reports no per-core loads, DeadWare uses Windows per-processor counters instead. Core traces are saved in the six-hour graph history for up to 48 cores, at most once a second (every two seconds above 32 cores); Windows fallback traces are live-only when no single CPU identity is available. The joined CPU / GPU pop-out, Usage history, Alerts and Cooling Health do not use per-core data. The option is off by default; the CPU card subtitle shows `· N cores` while it is on.

## Processes

Enable **Per-process monitoring** (Settings, Monitoring) to fill the **Processes** page; its **Turn on** button sets the same option. The option is off by default and applies at the next poll: while it is off, DeadWare runs no process scan. Processes with the same image name form one app row, and a row expands to its processes. The columns are CPU, Memory, I/O, Disk and Network by default; **PID**, **I/O read**, **I/O write**, **Disk read**, **Disk write**, **Download** and **Upload** are in the column picker, which remembers your choice. I/O is Windows' per-process I/O counters, available to every user; it is labelled I/O everywhere and is never disk data. Disk is physical drive traffic and Network is per-process traffic, and both need DeadWare to run as administrator: a standard user sees no Disk or Network columns, and the banner reads "Disk and network need administrator". A dash has a tooltip naming its reason. **End task…** ends the selected process or every process of the selected app, never a process tree, after a confirmation box whose default answer is **No**. Like Task Manager, it refuses System (PID 0 and 4), DeadWare itself, critical and protected processes and Windows' own processes (every Windows service host, lsass, dwm and services.exe); your own Windows tools such as Explorer, Command Prompt and Notepad can be ended. Third-party services and other users' processes can be ended only when DeadWare runs as administrator; otherwise they report "Needs administrator". Known limit: any process that runs as SYSTEM or another service account from a program inside the Windows folder (outside its `System32\DriverStore`) counts as Windows' own, so a third-party service installed there, as some older drivers are, is refused as a Windows process. **Open file location** opens the folder of the selected process. While **Record usage history on this device** is also on, DeadWare saves the busiest apps' CPU, memory and I/O for 30 days; see **Application resources** under Usage history.

## Desktop widget

The widget's pin control is in **Settings → Widget always on top**. Changes update an open widget immediately and are saved even when it is closed. Earlier saved widget pin choices carry over. Other graph windows keep their existing Always on top controls.

Choose the displayed graphs in **Settings → Widget graphs**: CPU/GPU usage, CPU/GPU temperature, RAM usage and Network activity. All four are enabled by default. **Connections map (live)** is a separate option, off by default. Use it alone or alongside any selected graphs. Choices are saved and apply immediately to an open widget. Hidden graphs keep collecting history. Turning graphs off lowers the minimum height while keeping your current size and pin choice; resize the widget to your preferred height. If all graphs and the map are off, the widget shows a hint to choose graphs in Settings.

The compact widget has a **Usage** graph with CPU and selected-GPU utilization together, followed by a **Temperature** graph with both devices' temperatures together. CPU uses the CPU theme color and a solid line in both graphs; GPU uses the GPU theme color and a dashed line in both. Small CPU/GPU legends show the current readings. Usage shares a 0–100% scale; temperature shares a °C scale that expands above 100°C when needed. A third **RAM** graph shows physical memory usage on a 0–100% scale, with current percent and used/total memory in its legend. A fourth **Network** graph shows download as a solid blue line and upload as a dashed green line on one bytes-per-second scale, with current rates in its legend. These graphs follow the shared history range and GPU selection, use saved graph history, and keep unavailable readings and downtime as gaps. The Connections map always uses current live observations, independently of the main page's History selection or playback. The map sits below the selected graphs. Its compact 2D view fills the available panel with only the map, without text labels, speed readouts or history controls. The small NA button switches between World and a closer North America view and saves the selection. In either view, drag the map to pan and use the mouse wheel to zoom; keyboard arrows and +/− work when the map has focus. Home resets the current region. Custom pan/zoom stays in place during live refreshes and Home-city changes, and resets when switching region or reopening the widget. Details remain on the main Connections page. The widget's minimum height follows the selected graphs and map; small work areas allow scrolling instead of clipping selected content.

## Connections

Both the main map and widget include subtle offline country borders. Connection arcs glow in their direction colors with a thin core line per active direction (two lanes when traffic flows both ways), moving dots travel along the busiest routes while traffic is active, nodes pulse and the origin shows as a radar mark; selecting or hovering a connection brightens its arc and shows its process, location and rates.

Open **Connections** beside Network for live observed destinations on a rotatable globe or a 2D world map. Drag, zoom, reset the view or pause animation, and filter by application, country and traffic direction. The compact list shows only nodes visible in the current map view, following rotation, zoom and the selected Live or History mode. Hover a node to see its application, location and current rates; click a node or its list entry to open a detail box beside it with application/PID, remote IP/port, TCP/UDP, approximate location, observed bytes, rates, coverage and observation times. The box follows the node, hides when it moves out of view, and closes with **Close** or **Escape**. Private/LAN, special and unlocated addresses remain in summary totals and saved-history CSV exports. This is observed traffic, so an idle socket need not appear.

Download/upload colors and moving highlights show observed direction; bounded marker sizes and path widths indicate relative volume. Quiet or stale traffic stays static, and stopped History does not animate. Live totals cover currently active peers since their first retained observation, rather than all session traffic. The map draws at most 256 grouped locations and discloses omitted groups. List entries show grouped-location byte totals; detail boxes identify a representative connection with its own rates and bytes, separately from location totals. Selecting a saved node reads its representative directly, including observations beyond the former table's first page. IPv6 endpoints use `[address]:port` notation.

**History** offers Today, 7 days, 30 days or a chosen interval, with a minute cursor and playback. Each saved row's rate is its recorded-minute bytes divided by 60 seconds, independent of the selected range. Incomplete minutes remain marked incomplete; the average does not imply continuous capture. Missing time, paused recording, capture loss, sleep and stopped capture remain gaps. Empty intervals do not invent traffic. The optional widget map continues showing live activity while this page shows history, and recording continues when the dashboard is hidden.

Location lookups use a local [DB-IP City Lite database](https://db-ip.com/db/download/ip-to-city-lite), credited to [DB-IP.com](https://db-ip.com/) under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The database is not bundled. **Download / update locations** explicitly contacts `download.db-ip.com` over HTTPS to fetch the monthly database; progress and cancellation are available, and a failed update keeps the previous valid database. There are no automatic database downloads or per-address online queries. Observed peer IPs are never submitted to a geolocation or DNS service. The download's own traffic may appear in Connections. Local lookups work offline afterward; Summary totals and history recording work without a location database; nodes and their details require located endpoints.

Choose an optional approximate **Home city** from the offline list under **Recording, origin and storage**. Animated connection paths require this origin, current located traffic, Live mode and Animate enabled. Until then, the map says **Unknown origin** and assigns this computer no geographic position. DeadWare does not request precise Windows location or discover your public IP online. Geographic results can be wrong or incomplete, especially with VPNs, CDNs and proxies. Curves illustrate endpoint links, not measured routes. An endpoint's city/country does not establish final data storage, the ultimate service location, or whether traffic is safe or threatening.

Connections recording is optional and **on by default**. Pause/resume it with the recording checkbox beside the location-database actions; rolling expiry continues while new recording is paused. Minute records in `%LOCALAPPDATA%\DeadWare\connections.db` retain application identity/name, remote IP/port, protocol, observed byte counts/times, completeness and the approximate location/origin available when recorded. A later location-database update does not relocate old records. History starts when this feature records; it cannot reconstruct earlier activity. Export the current filtered history to a new local CSV when needed.

History normally retains 30 days, with a 256 MiB primary-database cap and a bounded journal. High traffic can evict older whole minutes earlier; the page shows the actual earliest retained time. Intended older-history eviction can remain in effect even if a later write fails. Background writes target a 15-second flush interval and drain on normal **Quit DeadWare**. A crash or power loss can lose the unflushed batch; delayed or failed storage can extend that interval and produces incomplete/unavailable recording status. Storage failures leave live monitoring available. History stays in this Windows profile and is not uploaded or copied by source synchronization. Back up databases only while DeadWare is fully quit.

## Hardware compatibility

DeadWare discovers hardware rather than assuming a particular PC. [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) supplies supported sensor data; Windows counters provide basic fallbacks. Support varies by CPU, GPU, motherboard, laptop firmware, drivers and permissions. Missing sensors are shown as unavailable, and missing history remains a graph gap.

The default hardware scan focuses on CPU and GPU sensors. Extended motherboard, controller, storage and memory-device sensors are optional and off by default, since low-level polling can affect responsiveness on some machines. Changing this setting requires restarting DeadWare. Windows memory usage remains available without extended scanning. Drive temperature and health have their own **Storage sensors** switch under Settings → Monitoring, on by default, read every 30 seconds and applied after a restart; drive throughput and free space do not depend on it. ATA SMART health may need administrator rights.

This first release is **not complete HWiNFO sensor parity**. A successful launch on one PC is not evidence that every sensor works on every device. Please report compatibility findings through the hardware issue template with device models and the capability message, without serial numbers.

## Battery history

Open **Battery history** in the sidebar to see how charge drops and recovers, along with current charging status. The charge line shows Windows energy saver periods (battery saver before Windows 11 24H2): the normal solid line means saver off, dashed amber means saver on, and dotted gray means unknown state. A legend identifies each style. Choose **Open in window** for a separate resizable window; its position, size and Always on top choice are remembered. The Day/Week/Month/Year/All history selector is independent of the live graph range. When Windows reports no battery, the sidebar entry hides automatically; it returns if a battery is detected or its status is unknown. Saved battery history is kept.

DeadWare records the system battery total once per minute plus observed charging/power and energy saver state changes. On Windows 11 24H2 and later it reads Energy saver's own status, because the older battery-saver flag stays off in Energy saver's standard level; earlier Windows versions keep using that flag. Recording starts automatically on a battery-equipped device and can be paused without deleting saved history. Windows supplies these readings without administrator access. Unknown readings stay unavailable; a desktop with no battery says so. Multiple physical batteries appear as the combined system charge.

Observations are kept indefinitely in `%LOCALAPPDATA%\DeadWare\battery-history.db`, independently of the six-hour live graph cache and Cooling Health retention. There is no automatic expiry or size-based deletion. Storage usage and recording errors appear on the page. The database grows with recorded observations; long-range charts use bounded summaries without deleting originals. Dots show percentage averages and vertical lines show minimum–maximum in each displayed bucket. Hollow charge dots indicate mixed or unknown saver state within a summarized bucket. Green marks identify recorded charging and amber marks identify energy saver; filled marks mean all observations in a bucket reported that state, and outlined marks mean mixed states. They do not establish the state during unobserved time. Missing data, sleep, pauses and restarts remain gaps.

History begins with this version while DeadWare runs; earlier device history cannot be reconstructed. Writes flush every 15 seconds and on normal **Quit DeadWare**. Abrupt power loss can lose the unsaved batch. A storage problem reports an error while the other monitors continue. Resolve storage access and restart to retry. Battery data stays local to this Windows profile; source-code synchronization through GitHub does not copy it to another computer. Export the selected range to a new CSV for a backup, or copy the database while DeadWare is fully quit. Keep your own backup before resetting Windows or deleting the profile. Do not synchronize an open database.

## Usage history

Open **Usage history** in the sidebar, or **Open in window** for a separate resizable window whose position, size and Always on top choice are remembered. Choose **Day**, **Week** or **Month** and use **◀ Earlier** and **Later ▶** to step through past periods. Six charts cover CPU usage, CPU temperature, the dashboard's selected GPU's usage and temperature, RAM usage and network download/upload. Each point is the average of the recorded minutes in its slot, drawn over a shaded minimum–maximum band; minutes without readings stay empty and partial slots are not connected, so sleep, restarts and stopped monitoring remain visible as gaps. The MIN/AVG/MAX line under each chart uses the stored minute values for the whole period, not the drawn slots. Dates use local time.

The **Applications** table lists per-application download and upload totals for the period, summed by executable name across its processes, with a search box, a share bar and an **Other applications** row when more than 200 names were seen. Totals come from observed ETW traffic, so time without per-application capture is a gap, not zero traffic, and the page says how many recorded minutes had no capture. Different executables with the same name are combined. Open Connections to see where the bytes went.

**Application resources**, under Applications, ranks the apps that used the most CPU time, memory or I/O in the period, from the history saved while Per-process monitoring is on. Choose **Rank by** CPU time, Average memory or I/O. The table shows each app's CPU time, Avg CPU (its share of all logical processors across every recorded minute of the period, like the live CPU column), Avg memory while listed (private working set, averaged over the minutes the app was listed), I/O read, I/O written and Minutes listed, with a search box, a share bar of the period total and an **Everything else** row; it lists up to 200 apps, and when the period holds more the summary says so, for example "Top 200 of 320 applications". Select an app to chart it across the period in the ranked metric: CPU % of all logical processors, memory, or I/O read plus written per second. Minutes in which the app was not among the busiest are gaps, not zeros. A notice says how many minutes in the period have no process data (monitoring off, DeadWare not running, or a capture gap); minutes from before the 30 days are not counted, and a period that reaches back that far says they are not kept.

To see what was busy at a moment, click a point on the Device **CPU** or **RAM** chart; on the keyboard, Left and Right move between points and Enter lists one. The card lists that slot's busiest apps, ranked by CPU time from the CPU chart and by average memory from the RAM chart, scrolls into view and names the minutes listed in its heading (for example "Busiest apps · 03:13–03:16", with the date on Week and Month); a hairline marks the slot on both charts. **Clear** or Esc returns to the whole period, as do changing the range and **◀ Earlier** or **Later ▶**. A point can stand for several minutes: a Day point is a single minute only when the chart is at least 1,440 pixels wide. A slot recorded while monitoring was off says "No process data in this span."

DeadWare records one row per minute for each metric (average, minimum, maximum, sample count and whether the minute was complete) plus per-application bytes, in `%LOCALAPPDATA%\DeadWare\usage-history.db`. Recording is on by default; **Record usage history on this device** on the page or in Settings pauses it without deleting saved history. Rows are kept for 400 days, and the file is capped at 256 MiB with the oldest whole days dropped first, never the current day; the page shows storage use and the earliest retained minute. GPU rows are keyed by model name, so a change in enumeration order does not split them; two GPUs of the same model are ambiguous and not recorded. A restart inside a minute merges that minute and marks it incomplete. Writes run in the background every 15 seconds and flush on normal Quit; a crash or power loss can lose the unflushed batch. A storage problem reports an error on the page while live monitoring continues.

While **Per-process monitoring** and **Record usage history on this device** are both on, DeadWare saves each minute's busiest apps in `%LOCALAPPDATA%\DeadWare\process-history.db`: the top 10 by CPU time, by memory and by I/O, at most 30 apps, plus one Everything else row that holds the rest of the apps the scan saw, unnamed processes included. There is no separate switch; turning either off stops this recording and keeps what was saved until it is 30 days old. Apps are keyed by image name, ignoring case, as on the Processes page. Minutes are kept for 30 days: older days are removed when DeadWare starts and once a day, also while recording is off, and the card never shows them. The file is capped at 128 MiB with the oldest whole days dropped first, never the current day; a full day at the 30-app cap measured 3.4 MiB, so 30 such days fit. A minute is saved after it ends, so the newest minute appears on the card a minute or so later. Writes run in the background every 15 seconds and flush on normal Quit; a crash or power loss can lose the unflushed minutes. A restart inside a minute keeps that minute's first part and marks it incomplete. A newer, foreign or damaged file is kept and reported, never overwritten, and live monitoring continues. Known limits: usage after the last scan that saw a process is not recorded, nor is a process that starts and exits between two scans, so totals can be lower than the Device charts. CPU time and I/O in a saved minute are always numbers; when an app's counters cannot be compared for one scan, which is rare, that scan counts as 0, so a saved minute can understate an app rather than mark it unknown. Application resource history begins when 0.14.0 first runs with both switches on; earlier versions saved no process data.

History begins when version 0.7.0 first runs; the six-hour live graphs and their cache are separate and are not copied into the new store. Year and All ranges are not offered yet. Export the period's device minutes or application totals to a new CSV file; names that look like spreadsheet formulas are neutralized. Application names and byte totals describe what runs on this computer, so treat exports as private. Usage history, including `process-history.db`, stays in this Windows profile and is never uploaded; back up the databases only while DeadWare is fully quit.

## Alerts

Open **Alerts** in the sidebar. **Rules** lists the thresholds you have set; add one by choosing a kind, a target, a value and a duration, then **Add rule**. Four kinds are available. A **device metric** rule fires when CPU usage, CPU temperature, the dashboard's selected GPU's usage or temperature, or RAM usage is at or above the value for 1, 5, 15 or 60 consecutive recorded minutes. A **network rate** rule does the same for download or upload in MB/s. An **application traffic** rule fires when a named executable's download plus upload reaches a budget in MB within one local calendar day. A **battery** rule fires as soon as the charge is at or below a percentage while running on battery. Rules can be edited, switched off without deleting them, or removed.

While you type a threshold, the page shows what Usage history recorded in the last 7 and 30 days: the highest minute, the average and the share of recorded minutes at or above the value. That is the suggestion mechanism; DeadWare never sets a threshold for you.

Every crossing is one **episode**. When it starts, a tray balloon names the rule and the observed value; clicking it opens Alerts. **Recent alerts** lists episodes newest first with their peak and whether they are still open, with **Acknowledge** as a bookkeeping mark and **View in Usage history**, which opens the Day view around the episode so you can see the surrounding minutes. A rule notifies once per episode and re-arms after the metric stays below the threshold minus a small margin (3°C, 5 percentage points or 10% of a byte value) for the rule's duration; it never notifies more than once an hour, and an application budget notifies once per day. **Show tray notifications for alerts**, on the page and in Settings, mutes balloons for all rules while episodes are still logged. Cooling Health keeps its own warnings and notification setting.

Device and network rules evaluate the per-minute averages that Usage history records, so **Record usage history on this device** must be on for them, and what the log shows is exactly what the Usage history charts show. A minute without a reading neither counts nor resets; a recording gap such as sleep or a restart resets the consecutive count. Application budgets are seeded from the stored day at startup, so a restart mid-day keeps the morning's traffic. Rules are saved in `settings.json`; the log lives in `%LOCALAPPDATA%\DeadWare\alerts.db`, keeps 400 days under a 64 MiB cap, is written in the background and flushed on Quit, and is never uploaded. An alert means a threshold you chose was crossed in observed data; it is not a hardware diagnosis or a security finding.

## Cooling Health

The **Cooling Health** page saves local CPU/GPU temperature, usage and package power, plus clock and fan readings when supported. A GPU's fan speed comes from the card. A single CPU's fan speed comes from its cooler: a motherboard or AIO header labeled as a pump (for example `Pump Fan` or `AIO Pump`), otherwise the `CPU Fan` header. These readings need **Extended sensors**; unlabeled headers such as `Fan #2` are not used. Turning Extended sensors on or off changes the CPU sensor mapping, so its Cooling Health history and references start under a new identity. Recording starts by default; optional tray notifications start off. Choose a device and day/week/month range, switch metrics or export a new CSV file. Settings and the SQLite history database live under `%LOCALAPPDATA%\DeadWare`. No thermal data is uploaded. Per-application network data is not stored there.

The first minute produces a history window. To compare cooling, select a past period of up to seven days when you believe the setup was operating normally and save it as a named reference. At least 30 eligible minute windows are needed. The first five minutes, gaps, unstable workloads, missing required readings and known throttling are excluded; learning can therefore take longer than 35 minutes. Saved reference readings stay fixed rather than learning a developing problem as normal.

Comparisons need ten consecutive stable recent minutes, each matched to at least ten reference windows within 10% or 5 W of package power (whichever is larger), ten percentage points of load, and comparable fan speed when both sides provide it. The initial warning rule requires every recent minute to exceed the reference mean by at least 5°C and its 95th percentile by at least 3°C. These conservative engineering defaults are not validated probabilities of hardware failure. Coolant and room temperature are not measured by this first implementation; fan context may also be unavailable. Temperature-target boosting can conceal cooling deterioration, so an ordinary comparison is not a health certificate.

Warnings are logged even when tray notifications are muted. Enable notifications if desired; warnings can be acknowledged and are limited to one per device/reference per 24 hours. An unacknowledged warning suppresses repeats. Changing the active reference does not modify its saved readings. Choose **New cooling setup** after hardware replacement (including a replacement with the same model), cleaning, remounting, fan-curve or power-limit changes. Local identity uses machine, hardware metadata and the selected sensor mapping; it cannot identify every physical replacement automatically. When multiple devices have identical model names, their histories are separated by session and comparison is disabled because enumeration cannot establish physical identity. Older setups remain available for history viewing.

By default, minute detail is retained for 30 days and hourly summaries for 90 days. Controls offer 7/30 days of detail and 30/90 days of summaries. The database is capped at 256 MiB with a bounded journal; the page shows storage usage. Up to ten references per device/setup are retained. If storage is locked, full or corrupt, recording reports an error and live monitoring continues; resolve the storage issue and restart to retry. Saved references can consume space independently of ordinary history retention. Database files are local to this Windows profile; cloud synchronization of an open database is not supported.

Cooling Health flags changes worth investigating. It cannot diagnose a blocked cooler, failing pump, or remaining lifespan. Pump speed is recorded as CPU fan context when a labeled pump header is available, but RPM alone cannot show flow; flow and coolant monitoring are not included yet.

## Network measurements and privacy

Interface totals work independently of per-process attribution. Application traffic uses Windows ETW metadata, including TCP/UDP IPv4/IPv6 byte events. Connections optionally saves endpoint metadata locally as described above; recording starts enabled. The Processes page's live per-process data stays in memory. While Per-process monitoring and usage history recording are both on, the busiest apps' image names (never program paths) and their CPU, memory and I/O are saved for 30 days in `process-history.db`, as Usage history already saves network per app. The program paths of monitored processes are never saved or logged; Open file location and End task read one only when you use them. DeadWare's own program path is stored only where DeadWare needs it: in its **Start with Windows** task while that is on, in an update's handoff files in the `updates` directory, and in the opt-in layout trace. The app never collects packet payloads, URLs, messages or file contents, and does not upload observed endpoints, application names or histories. No firewall management is included.

Rates reflect observed traffic, not ISP billing totals. Adapter totals and attributed application traffic may differ due to virtual adapters, local traffic, protocol overhead or lost events. The combined network graph's last six hours are stored locally; per-application activity and names are not persisted in that graph cache. Connections history is separate, optional and bounded. Thermal and usage history are stored separately as described above. Settings are kept in the user's local application-data directory. Explicit location-database downloads contact DB-IP's download host; update checks/downloads contact GitHub.

Diagnostic output is generated only when explicitly requested. It can include hardware names and running application information; redact it before attaching it to a public issue.

For local troubleshooting, `DeadWare.exe --diagnose output.json --samples 3` collects a short sample and exits. Add `--no-hardware` to isolate Windows counters and network tracking, `--no-etw` to isolate hardware collection from per-app tracing, or `--no-processes` to leave out the process scan. Diagnostics include provider timings. The process scan adds only counts and timings, with no process names or paths, but each sample's existing per-app network list can name apps that used the network; add `--no-etw` to leave it out. Avoid enabling extended sensors when investigating a responsiveness problem.

For workspace-saving problems, start the app with `--layout-diagnostics "C:\path\layout.jsonl"` using an absolute local output path. This opt-in, size-limited trace records settings paths, open-window IDs and save results; it follows an administrator restart and contains no sensor readings or network traffic. Use a new file or a previous DeadWare layout trace. Treat it as private diagnostic data.

## Build

Install the stable [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) on Windows, then:

```powershell
dotnet build DeadWare.slnx -c Release
dotnet test DeadWare.slnx -c Release
dotnet run --project src/DeadWare.App/DeadWare.App.csproj
```

Create a self-contained portable ZIP and SHA-256 checksum:

```powershell
pwsh -File scripts/publish.ps1 -Version 0.14.0
```

The packaging script runs tests before publishing, bundles the independent self-contained update helper, and records all managed file hashes in `deadware-package.json`. Output goes under `artifacts/`. GitHub Actions runs the same script. Pushing a normal three-part version tag such as `v0.6.0` builds and publishes a normal release after tests pass, using the matching `docs/releases/v0.6.0.md` notes. Workflows use pinned action commits.
