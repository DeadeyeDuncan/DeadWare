## Features

- CPU and GPU utilization and temperature graphs with detected device names, drawn as smooth curves on a hairline grid with wall-clock time ticks and a hover readout of the time and values at any sample.
- Optional GPU fan RPM on temperature graphs, with a separate scale and saved history.
- Optional CPU pump RPM on CPU temperature graphs, with its own setting, the same left RPM scale and saved history.
- Optional per-core CPU usage: thin lines under the bold total on the usage graphs, with a hover list of the busiest cores.
- Drive monitoring: a Disk card with total and per-drive read/write throughput, a Storage page with temperature, health, wear and free space per volume, an optional widget Disk graph, a six-hour per-drive history (up to 8 drives) and drive temperatures as Storage devices in Cooling Health. Temperature and health come from the **Storage sensors** switch (on by default).
- A combined download/upload graph with a shared scale and distinct line styles.
- Per-application network rates when Windows permits ETW capture.
- Processes: CPU, memory and I/O per app for every user; GPU and GPU memory per app, expected to need no administrator rights but not yet checked in a standard-user session; and physical Disk and Network per app as administrator, with expandable processes, a column picker, **End task…** and **Open file location**. Per-process monitoring is off by default.
- Connections: a filled native globe or 2D map with glowing traffic arcs, moving dots on busy routes and hover chips, a visible-node list and connection detail boxes, a Destinations table of every destination, local saved history with a traffic strip of the busiest applications, and an optional live widget map.
- Searchable sensor readings with minimum, maximum and average values.
- Selectable graphics adapters on multi-GPU systems.
- Separate or joined CPU/GPU graph windows and a compact widget with usage, temperature, RAM and network charts and always-on-top controls.
- Compact pop-out graphs prioritize the current reading and chart; their options menu holds history range, Always on top and sensor statistics.
- Close the dashboard to the system tray and keep graphs, the widget and monitoring running independently.
- Restore the graphs and widget left open, including their saved positions and sizes.
- Optional administrator startup at your Windows sign-in, available only from a protected folder such as `C:\Program Files\DeadWare`.
- Shared 1-, 5- and 15-minute plus 1-, 3- and 6-hour graph ranges; all windows use one collector. Choose a range from the segmented control in the dashboard header or in a pop-out's **⋯** menu. The selected range stays synchronized across windows. The choice and recent CPU/GPU/RAM/network traces are saved locally across quits and computer restarts. Cooling Health's longer saved history is separate. At 1–6 hours, a per-pixel average line shows the trend and a faint min/max band retains spikes and variation. Missing readings remain gaps, and displayed statistics use the actual readings. Short ranges retain their detailed traces. In **Settings → Appearance**, turn **Smooth long-range graphs (1, 3 and 6 hours)** off to use raw traces across the dashboard, pop-outs and widget. The choice is saved; raw traces retain observed peaks and gaps without the average/range band.
- Local Cooling Health history, fixed reference comparisons, CSV export and optional sustained-change warnings. With **Extended sensors** on, CPU fan speed comes from a labeled pump or CPU Fan header.
- Lifetime battery-percentage history with recorded charging and Windows energy saver (battery saver) periods, Day/Week/Month/Year/All views, CSV export and a separate remembered window.
- Usage history: Day/Week/Month views of CPU and GPU usage and temperature, RAM and network, per-application download/upload totals, CSV exports and a separate remembered window, kept for up to 400 days. With Per-process monitoring on, **Application resources** ranks the busiest apps' CPU, memory, I/O and GPU, kept for 30 days, and clicking a CPU, RAM or GPU point lists that moment's busiest apps.
- Alerts: your own thresholds on CPU, GPU, RAM, network rate, an application's daily traffic or battery charge, with tray notifications, a 400-day log and a jump to the Usage history minutes behind each alert.
- Lighting: your PC's RGB lights through a copy of OpenRGB that you install, with **Lights on**, brightness, one colour for every zone with Undo, colours for single zones, a brightness and colour correction of its own for each device, lighting modes for keyboards, painting single keys, layers (colours, effects, key fades and key ripples) and saved looks for keyboards, the Wave, Breathing and Spectrum effects, which keep running with the window closed, and a drawing of your desk: a built-in picture of the desk and the inside of the PC on one known rig, otherwise a plain desk that you arrange so Wave crosses it in the right order. Off by default.
- Startup and manual GitHub release checks, update-available notices, verified user-initiated updates and rollback to the previous installed version.
- Update downloads clean up after themselves, and installations in a protected folder update through an administrator-only update folder.
- A native Windows interface (WinUI 3): light or dark mode and the accent colour follow your Windows settings, on a solid background that keeps its colour whether or not the window has focus. Windows High Contrast is honoured. The colour themes and **Window glass** of 0.17 and earlier are not part of this interface.
- Panels are cards, the sidebar marks the current page, the page header is one row holding the page title, a hardware subtitle and the shared controls (on Overview its graphics card choice, the history range and **Open widget**), and Settings groups its options into seven tabs: **Monitoring**, **Appearance**, **Widget**, **Pop-outs**, **Startup**, **History and alerts** and **Lighting**. Monitoring opens by default; **Sensor sources** in Monitoring and **Repair startup registration** in Startup are collapsed expanders.
- Live graphs slide continuously between readings on the short ranges. Where a reading would move a graph by less than half a pixel (15 minutes and longer at 0.5-second polling on a typical card), or while Windows animation effects are off, the graph stands still and moves on a pixel at a time, so long ranges cost almost nothing to keep current.
- Click a colour dot in an Overview card's header (one per trace; the GPU fan and CPU pump dots show while their lines do), or open **Settings → Appearance → Graph lines** and pick a trace, then choose its colour, **Default / Solid / Dashed / Dotted** pattern, **Line thickness** (50–300%) and optional **Neon glow** with glow strength (0–300%). 100% preserves the original thickness/glow. Choices are saved and shared with pop-outs, widget traces and legends; download and upload have separate colors, and each CPU core has its own entry once per-core usage has a reading. Choose **Default colour** to clear a custom color; choose **Default** under Line pattern, return both sliders to 100%, and turn off glow to restore the original trace style. While per-core CPU usage is shown, the CPU card's dot also lists each core's line and the actions that copy the CPU line's style to every core.
- The Overview chart grid uses one, two or three columns to fit the available page width.
- The Processes page shows action results and scan status inside its search card, and folds its column definitions into **About these columns** under the table.
- The Updates page keeps versions, actions, progress and status in one card above the release notes, and folds its explanation into **How updates and rollback work**.
- The Sensors page shows its sensor count and statistics range in the search card, above the table.

## Download and run

Get the Windows x64 ZIP from the [latest release](https://github.com/DeadeyeDuncan/DeadWare/releases/latest) or browse [all releases](https://github.com/DeadeyeDuncan/DeadWare/releases). Extract the **entire** archive and run `DeadWare.exe` inside the `DeadWare` folder. The .NET runtime is bundled. The app is portable and unsigned. Version 0.6.0 adds manual update and rollback controls; older installations need one complete ZIP upgrade to gain those controls.

Windows 11 and Windows 10 version 2004 or later, x64, are the target. ARM64 and other operating systems are not validated. Hardware coverage varies by device.

Start as a normal user. If a capability needs additional permissions, the app shows its status and provides an explicit administrator restart action. Administrator access does not guarantee every sensor is available. DeadWare does not disable Windows protections or install a custom monitoring driver.

## Updates and rollback

DeadWare checks the latest normal release in `DeadeyeDuncan/DeadWare` once after starting, without delaying monitoring. When a newer version is available, a dashboard banner appears outside the Updates page and a system-tray notification lets you know; **Review update** opens Updates. You choose when to download and install it with **Update & restart**. You can also choose **Check for updates** on that page at any time. Checks do not download app packages or install anything. Draft/preview releases and source commits are excluded, and an installed newer build stays on its current version. Offline or rate-limit errors appear on Updates without interrupting startup. There is no recurring polling while the app remains open.

Release notes include every normal release newer than the installed version through the offered update, newest first, with separate version headings. If earlier notes cannot be loaded, the page keeps the latest notes and explains the missing history. Installation still uses the latest eligible package.

Choose **Show release note history** in Updates to browse all normal published versions, including the installed version and older releases, newest first. Each explicit opening refreshes the history from GitHub; it is not fetched at startup. **Hide release note history** returns to the usual current or missed-version notes. Loading can be cancelled, and a failed history request can be retried without changing the offered update.

When an eligible update is available, **Update & restart** downloads the complete Windows x64 ZIP, checks its SHA-256 digest/checksum and validates the package's file manifest. Download/preparation can be cancelled. Once the installer is ready, DeadWare performs its normal Quit to save settings and drain history, replaces only managed app files, and restarts at the same path with remembered windows. Settings and battery/Cooling Health/live graph databases stay in `%LOCALAPPDATA%\DeadWare`.

**Roll back & restart** restores the previous verified installed version, keeping current settings and recordings. The first updater-enabled installation may have no registered rollback; one becomes available after an in-app update. Only a verified older backup is offered. If replacement or startup fails, the helper restores the previous app when the failed process has exited. It never forcibly terminates monitoring or overwrites a still-running replacement. A running app that did not confirm startup must be quit normally before rollback/recovery can proceed.

Updates require the complete packaged app directory, including `deadware-package.json` and `DeadWare.Updater.exe`, and permission to write app files. Shortcuts and Windows startup keep their existing executable path. Verification failures, offline checks and unavailable backups leave the current installation intact. Update checks/downloads contact GitHub and do not upload monitoring data. Update staging, the previous snapshot and operation results are stored in an `updates` directory partitioned by installation path: `%LOCALAPPDATA%\DeadWare\updates` for copies in user folders, and the administrator-only `%ProgramData%\DeadWare\updates` for an installation in a protected folder such as `C:\Program Files\DeadWare`, so programs without administrator rights can't change a downloaded update. Updating a protected installation needs **Restart as administrator**, and rolling back to a version older than 0.6.39 isn't available for it.

If an installed app file or the saved rollback copy has been changed or damaged, Updates shows a message and disables installing until you reinstall the complete package. Opening Updates also cleans up old downloads: only small records of the latest update are kept (its downloaded ZIP and unpacked copy are removed), and abandoned update folders older than a day are deleted. For an installation in a protected folder, this cleanup happens when DeadWare runs as administrator. Update data that an earlier version left for such an installation in `%LOCALAPPDATA%\DeadWare\updates` isn't cleaned up automatically; you can delete it while DeadWare is quit.

New tagged versions are published as normal GitHub releases with ZIP/checksum assets. Older historical previews remain archived and are ignored by the updater. Publishing a release is separate from pushing source to a branch or opening a pull request.

## Startup and saved workspace

In **Settings → Monitoring → Data polling interval**, choose 0.5, 1, 2, 5 or 10 seconds. One second is the default. Changes are saved and apply after the current wait or reading finishes, without restarting. Faster polling uses more resources; slow hardware may take longer than requested. Every window shares this collector, and the display refreshes twice per second at the fastest setting. The six-hour graph range is retained. Cooling Health records at every setting, but 5- and 10-second polling has too few samples per minute for its reference comparisons.

In **Settings → Startup**, enable **Start with Windows** to launch DeadWare as administrator when you sign in. Windows approval is needed to configure this option. It creates a task for your Windows account, runs only in your signed-in session, and stores no password. You can turn it off from the same page. Only one monitoring instance runs at a time.

DeadWare must be in a folder standard users can't change, such as `C:\Program Files\DeadWare`, to start as administrator at sign-in. A copy in a user folder (for example `AppData\Local\Programs` or Downloads) can't turn this on, and Settings explains why. If startup was already on from such a folder, Settings shows a warning: copy or extract DeadWare into `C:\Program Files\DeadWare` with administrator approval, start DeadWare from that copy, then open **Settings → Startup → Repair startup registration** and choose **Enable / repair startup**, or turn startup off. Startup is never turned off automatically.

For a quiet sign-in, also enable **Start in the system tray** in **Settings → Startup**. This hides the dashboard only for Windows startup launches. Remembered graphs and the widget still reopen when restoration is enabled in **Settings → Pop-outs**; turn restoration off too if you want only the tray icon. A fresh manual launch still shows the dashboard. If the tray icon cannot be created, the dashboard stays accessible.

Closing the dashboard with its X or Alt+F4 hides it in the system tray. Pop-out graphs, the widget and monitoring keep running, even with no dashboard open. Double-click the DeadWare tray icon or right-click it and choose **Show dashboard** to reopen it. Windows may place the icon in the hidden-icons area next to the clock. The menu also has a lights line between **Show dashboard** and **Quit DeadWare**: **Turn lights off** or **Turn lights on**, or **Lights (not available)** (greyed out) when **Enable lighting** is off in Settings, or the lighting helper isn't connected or is still starting (see Lighting, below).

To fully stop monitoring, choose **Quit DeadWare** from the tray menu or dashboard. Keep window restoration enabled and leave your desired graphs and widget open when you quit: they will reopen with their saved positions, sizes and always-on-top choices. Closing a graph or widget individually keeps it closed next time. Positions are kept within available monitors if your display setup changes. Recent graph history and saved Cooling Health history remain available after quitting. Hiding the dashboard resets neither.

Graph history is saved automatically in `%LOCALAPPDATA%\DeadWare\live-graph-history.db`, independently of Cooling Health recording. It retains the last six elapsed hours of CPU/GPU usage and temperature, GPU fan and CPU pump RPM, RAM usage percentage and combined download/upload rates. RAM uses a 0–100% scale with current used/total memory shown beside it; its history begins with readings collected in version 0.6.11 or later. GPU fan history begins with readings collected in version 0.6.20 or later; earlier samples remain unavailable. Time while DeadWare was stopped remains a gap; after more than six hours away, the old readings fall outside the available range. Current values always come from fresh readings. Writes run in the background every 15 seconds and flush on normal quit; a crash or abrupt power loss can lose the latest unsaved batch. The database is capped at 64 MiB with a bounded journal. A save error is shown in the dashboard status while live monitoring continues.

Restoration matches local machine and hardware metadata, including GPU model/type rather than enumeration order. Ambiguous identical-model GPUs are not restored; an indistinguishable same-model physical replacement cannot always be detected. Full sensor-table statistics and the Network page's per-application traffic totals remain current-session data. Connections has its own optional saved endpoint history, described below. The first upgrade from a version without graph persistence cannot recover its earlier in-memory traces.

Version 0.1.0 saved window positions but did not record which windows were open. After upgrading, arrange your desired windows once to establish the saved workspace.

Startup points to the executable's current location. Keep the extracted folder in a permanent location. If you relocate it, start DeadWare from the new location and enable startup again there. To put it in a protected folder such as `C:\Program Files\DeadWare`, copy or extract it with administrator approval instead of moving it with Explorer on the same drive, which keeps your account as the folder's owner. Disable startup before removing the app. Choose **Quit DeadWare** before replacing files during an upgrade; closing the dashboard alone leaves it running.

## Graph pop-outs

Use the overview cards' **Pop out** buttons to open graphs. In **Settings → Pop-outs**, enable **Join CPU and GPU graphs in pop-outs** to put CPU and selected-GPU usage together on one chart, and both temperatures together on another. The option is off by default. CPU keeps its theme color and solid line in both charts; GPU keeps its own color and dashed line. Both current readings and device statistics are available, with a shared 0–100% usage scale and a shared temperature scale that expands above 100°C when needed.

The choice applies to new pop-outs. Existing open windows and remembered layouts keep their current form, and joined and separate windows remember their own positions, sizes and pin choices. RAM, Network and Battery history windows keep their existing behavior. Open the widget from the dashboard's **Open widget** button.

In **Settings → Appearance**, enable **Show GPU fan speed on temperature graphs** to add the selected GPU's first reported fan RPM to the dashboard GPU temperature graph, separate or joined GPU temperature pop-outs, and the widget temperature graph. This saved option is off by default and applies immediately to open graphs. Fan speed uses a dotted line in the theme's warning color (amber by default) and a separate left RPM scale; temperature keeps the right °C scale. A missing fan reading stays unavailable and leaves a gap. A reported 0 RPM is a valid stopped-fan reading.

In **Settings → Appearance**, enable **Show CPU pump speed on CPU temperature graphs** to add the CPU cooler's pump RPM to the dashboard CPU temperature graph, the CPU temperature pop-out and the widget temperature graph. The joined CPU / GPU temperature pop-out keeps only the GPU fan. DeadWare reads a motherboard or AIO header labeled as a pump (for example `Pump Fan` or `AIO Pump`), otherwise the `CPU Fan` header; unlabeled headers such as `Fan #2` are not used. This needs **Extended sensors** and a single CPU. The option is off by default and separate from the GPU fan option. The pump uses a dotted line in the theme's download color (blue by default) on the left RPM scale; when the widget shows both, the GPU fan and pump share that scale. Change its color and line style with the CPU pump color button on the overview's CPU temperature card.

Enable **Show per-core CPU usage on usage graphs** (Settings, Monitoring) to draw one thin solid line per core under the bold total on the dashboard CPU usage card, the separate CPU usage pop-out and the widget Usage graph. Each line is tinted from the CPU graph colour and has no fill, glow or min/max band; on the 1–6 hour ranges the lines follow the smoothing setting as average lines. Hover a graph to see the eight busiest cores (`Core n · v%`) followed by `+N more`. A line is one LibreHardwareMonitor load sensor (`CPU Core #k`, `P-Core #k`, `E-Core #k`); where the chip exposes threads, each thread is a line, so SMT and hybrid chips show logical processors. Labels are positional (`Core 1…N`) and up to 64 lines are drawn. If LibreHardwareMonitor reports no per-core loads, DeadWare uses Windows per-processor counters instead. Core traces are saved in the six-hour graph history for up to 48 cores, at most once a second (every two seconds above 32 cores); Windows fallback traces are live-only when no single CPU identity is available. The joined CPU / GPU pop-out, Usage history, Alerts and Cooling Health do not use per-core data. The option is off by default; the CPU card subtitle shows `· N cores` while it is on.

## Storage

The Storage page shows every drive at once, one card each, named by its letters and then its model (for example "C: Samsung SSD 980 PRO 1TB") as everywhere DeadWare names a drive, and scrolls: the drive's read and write rates with their range statistics and chart, then its mounted volumes and health details. A drive whose health the hardware library cannot judge, such as some NVMe drives in USB enclosures, reads **Unknown**, not OK.

## Processes

Enable **Per-process monitoring** (Settings, Monitoring) to fill the **Processes** page; its **Turn on** button sets the same option. The option is off by default and applies at the next poll: while it is off, DeadWare runs no process scan. Processes with the same image name form one app row, and a row expands to its processes. The columns are CPU, Memory, I/O, Disk, Network, GPU and GPU memory by default; **PID**, **I/O read**, **I/O write**, **Disk read**, **Disk write**, **Download**, **Upload**, **GPU engine** and **Shared GPU memory** are in the column picker, which remembers your choice. A column list you saved in 0.13 or 0.14 that still holds exactly the old defaults gains GPU and GPU memory once; any list you customized is kept as it is. I/O is Windows' per-process I/O counters, available to every user; it is labelled I/O everywhere and is never disk data. Disk is physical drive traffic and Network is per-process traffic, and both need DeadWare to run as administrator: a standard user sees no Disk or Network columns, and the banner reads "Disk and network need administrator". GPU is the app's busiest GPU engine on any adapter, as in Task Manager, and **GPU engine** names it (for example "GPU 1 · 3D"); GPU memory is dedicated video memory. GPUs are numbered in the order Windows (DXGI) lists its graphics adapters, which usually but not always matches Task Manager's numbers; the GPU engine tooltip names the adapter. GPU values come from Windows' GPU performance counters and are read behind Per-process monitoring: every poll while the Processes page is open, every 5 seconds otherwise, which is enough for Usage history. They are expected to need no administrator rights, so that a standard user sees them too; that has not yet been checked in a standard-user session. A process that has not used the GPU shows 0 %. A new app shows a dash ("first sample") until two GPU counter readings have been taken more than a second after it started, usually one or two polls. A dash has a tooltip naming its reason. **End task…** ends the selected process or every process of the selected app, never a process tree, after a confirmation box whose default answer is **No**. Like Task Manager, it refuses System (PID 0 and 4), DeadWare itself, critical and protected processes and Windows' own processes (every Windows service host, lsass, dwm and services.exe); your own Windows tools such as Explorer, Command Prompt and Notepad can be ended. Third-party services and other users' processes can be ended only when DeadWare runs as administrator; otherwise they report "Needs administrator". Known limit: any process that runs as SYSTEM or another service account from a program inside the Windows folder (outside its `System32\DriverStore`) counts as Windows' own, so a third-party service installed there, as some older drivers are, is refused as a Windows process. **Open file location** opens the folder of the selected process. While **Record usage history on this device** is also on, DeadWare saves the busiest apps' CPU, memory, I/O and GPU for 30 days; see **Application resources** under Usage history.

## Desktop widget

The widget's pin control is in **Settings → Widget → Widget always on top**. Changes update an open widget immediately and are saved even when it is closed. Earlier saved widget pin choices carry over. Other graph windows keep their existing Always on top controls.

Choose the displayed graphs in **Settings → Widget → Widget graphs**: CPU/GPU usage, CPU/GPU temperature, RAM usage and Network activity. All four are enabled by default. **Connections map (live)** is a separate option, off by default. Use it alone or alongside any selected graphs. Choices are saved and apply immediately to an open widget. Hidden graphs keep collecting history. Turning graphs off lowers the minimum height while keeping your current size and pin choice; resize the widget to your preferred height. If all graphs and the map are off, the widget shows a hint to choose graphs in Settings.

The compact widget has a **Usage** graph with CPU and selected-GPU utilization together, followed by a **Temperature** graph with both devices' temperatures together. CPU uses the CPU line colour and a solid line in both graphs; GPU uses the GPU line colour and a dashed line in both. Small CPU/GPU legends show the current readings. Usage shares a 0–100% scale; temperature shares a °C scale that expands above 100°C when needed. A third **RAM** graph shows physical memory usage on a 0–100% scale, with current percent and used/total memory in its legend. A fourth **Network** graph shows download as a solid blue line and upload as a dashed green line on one bytes-per-second scale, with current rates in its legend. These graphs follow the shared history range and GPU selection, use saved graph history, and keep unavailable readings and downtime as gaps. The Connections map always uses current live observations, independently of the main page's History selection or playback. The map sits below the selected graphs. Its compact 2D view fills the available panel with only the map, without text labels, speed readouts or history controls. The small NA button switches between World and a closer North America view and saves the selection. In either view, drag the map to pan and use the mouse wheel to zoom; keyboard arrows and +/− work when the map has focus. Home resets the current region. Custom pan/zoom stays in place during live refreshes and Home-city changes, and resets when switching region or reopening the widget. Details remain on the main Connections page. The widget's minimum height follows the selected graphs and map; small work areas allow scrolling instead of clipping selected content.

## Connections

Use the toolbar at the map's top-right for Globe / 2D, zoom, Reset and Animate; at page widths of 1,100 DIP or more, the visible-node list sits beside the map, moving underneath on narrower windows. The lower card groups **Traffic** and **Destinations** in tabs (Live shows Destinations; entering History selects Traffic), and database downloads, recording, Home city and storage controls now live in the collapsed **Location database, recording and storage** section.

Both the main map and widget include subtle offline country borders. Connection arcs glow in their direction colors with a thin core line per active direction (two lanes when traffic flows both ways), moving dots travel along the busiest routes while traffic is active, nodes pulse and the origin shows as a radar mark; selecting or hovering a connection brightens its arc and shows its process, location and rates.

Open **Connections** beside Network for live observed destinations on a rotatable globe or a 2D world map. Drag, zoom, reset the view or pause animation, and filter by application, country and traffic direction. The compact list shows only nodes visible in the current map view, following rotation, zoom and the selected Live or History mode. Hover a node to see its application, location and current rates; click a node or its list entry to open a detail box beside it with application/PID, remote IP/port, TCP/UDP, approximate location, observed bytes, rates, coverage and observation times. The box follows the node, hides when it moves out of view, and closes with **Close** or **Escape**. Private/LAN, special and unlocated addresses are listed in the Destinations table (special-purpose ones under All only) and in saved-history CSV exports. This is observed traffic, so an idle socket need not appear.

The **Destinations** table below the map lists every destination the filters allow, in Live and in History: one row per remote address, adding every application and port that reached it, with its class, approximate location, applications, ports and traffic. Live shows current rates, received and sent bytes and observed connections for peers active in the last 60 seconds; History shows saved bytes, minutes with traffic and the first and last time seen. Search for an application to read that application's numbers for each destination. **Show** All, Internet or Local narrows the table and **Export destinations…** only; special-purpose addresses (shared CGNAT, multicast, broadcast, documentation and other reserved ranges) are listed under All only and count as neither local nor unlocated. The choice is remembered. Each choice lists its top 1,000 destinations by traffic (received + sent), and a row names its 10 busiest applications and ports; the count line above the table always gives every count, exact. The table sorts by RECEIVED, busiest first; click a header to sort by it. Rows update in place: while the pointer rests on the table, while its menu is open and for 3 seconds after an arrow, Page Up, Page Down, Home or End key in it, new data keeps the order and new rows join at the bottom; F5 re-sorts at once. Selecting a row highlights that address's nodes on the map (in History, up to 8 of its saved locations) and turns the map to them if none is in view; a line under the table says how many nodes are highlighted or why the address is not on the map. Esc clears the selection. Ctrl+C or **Copy row** in the row menu copies the row's cells as one tab-separated line, and **Copy address** copies only the address. **Export destinations…**, in History only, writes every destination in the chosen scope for the whole filtered interval to a new CSV, with no 1,000-row limit and up to 100 application names and 1,000 ports per row; the minute cursor does not narrow it. In History the table follows the minute cursor and lists saved minutes, so a minute appears a few seconds after it ends.

Download/upload colors and moving highlights show observed direction; bounded marker sizes and path widths indicate relative volume. Quiet or stale traffic stays static, and stopped History does not animate. The animation runs at about 30 frames a second while you use the map, slows to 15 after a minute without input and to 10 after five, and stops while the map is hidden, minimised, scrolled out of view or covered by other windows, or while Windows animation effects are off. Live totals cover currently active peers since their first retained observation, rather than all session traffic. The map draws at most 256 grouped locations and discloses omitted groups. List entries show grouped-location byte totals; detail boxes identify a representative connection with its own rates and bytes, separately from location totals. Selecting a saved node reads its representative directly, including observations beyond the former table's first page. IPv6 endpoints use `[address]:port` notation. The Destinations table lists bare addresses, since no port follows.

**History** offers Today, 7 days, 30 days or a chosen interval, with a minute cursor and playback. Each saved row's rate is its recorded-minute bytes divided by 60 seconds, independent of the selected range. Incomplete minutes remain marked incomplete; the average does not imply continuous capture. Missing time, paused recording, capture loss, sleep and stopped capture remain gaps. Empty intervals do not invent traffic. In the **Traffic** tab under the map, a traffic strip stacks the six applications with the most traffic in the interval, plus Other, as average rates over each slot's recorded time (1-minute slots for Today, 10-minute for 7 days and 30-minute for 30 days); it follows the Direction filter, and its colours identify applications, not direction. Time that was not recorded is hatched, never drawn as zero, and partly recorded slots are fainter. The minute in progress is not saved yet, so the right edge of Today stays empty and its hover says "Not saved yet". Click the strip to turn the minute cursor on at that minute; with the strip focused, Left and Right move the cursor to the first minute of the previous or next recorded slot, and Enter to the selected one. Click an application in the strip's legend to show only that application everywhere on the page; **Application: … ✕** clears it. The optional widget map continues showing live activity while this page shows history, and recording continues when the dashboard is hidden.

Location lookups use a local [DB-IP City Lite database](https://db-ip.com/db/download/ip-to-city-lite), credited to [DB-IP.com](https://db-ip.com/) under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The database is not bundled. **Download / update locations** explicitly contacts `download.db-ip.com` over HTTPS to fetch the monthly database; progress and cancellation are available, and a failed update keeps the previous valid database. There are no automatic database downloads or per-address online queries. Observed peer IPs are never submitted to a geolocation or DNS service. The download's own traffic may appear in Connections. Local lookups work offline afterward; Summary totals and history recording work without a location database; nodes and their details require located endpoints.

Choose an optional approximate **Home city** from the offline list under **Location database, recording and storage**. Animated connection paths require this origin, current located traffic, Live mode and Animate enabled. Until then, the map says **Unknown origin** and assigns this computer no geographic position. DeadWare does not request precise Windows location or discover your public IP online. Geographic results can be wrong or incomplete, especially with VPNs, CDNs and proxies. Curves illustrate endpoint links, not measured routes. An endpoint's city/country does not establish final data storage, the ultimate service location, or whether traffic is safe or threatening.

Connections recording is optional and **on by default**. Pause/resume it with the recording checkbox beside the location-database actions; rolling expiry continues while new recording is paused. Minute records in `%LOCALAPPDATA%\DeadWare\connections.db` retain application identity/name, remote IP/port, protocol, observed byte counts/times, completeness and the approximate location/origin available when recorded. A later location-database update does not relocate old records. History starts when this feature records; it cannot reconstruct earlier activity. Export the current filtered history to a new local CSV when needed. Apps in **Don't record these apps** show live, marked not recorded, and are never saved, and **Clear history…** under **Location database, recording and storage** removes saved history ([Usage history](#usage-history)); after an all-apps clear made while the clock was ahead, setting the clock back hides new Connections history until the clock catches up.

History normally retains 30 days, with a 256 MiB primary-database cap and a bounded journal. High traffic can evict older whole minutes earlier (a steady 20 application–destination pairs a minute fill the cap in about 8–9 days; idle and light use keep the full 30 days); the page shows the actual earliest retained time. An interval that reaches back before it shows a "Not kept" band on the strip and "Not kept before …" under it. "Capacity shortened retention" is added there, and in the capture line, only while the cap has removed minutes that the 30 days would still keep; once those minutes would have expired anyway, it no longer shows. Rows saved by versions before 0.16.0 stay until they expire, and the file does not shrink. A 7- or 30-day view on a full file takes a few seconds to read while "Reading saved history…" shows; an interval that holds too many saved rows to group says so and shows History as unavailable. Intended older-history eviction can remain in effect even if a later write fails. Each minute is saved as one row per application and destination shortly after it ends: 2 seconds plus one to two polling intervals, which is 3–4 seconds at the default 1-second polling. The minute in progress is saved on normal **Quit DeadWare**, within 15 seconds of pausing recording, and at Windows sign-out or shutdown when its 3-second limit allows. History and CSV export show a minute once it is saved. A crash or power loss can lose about the last minute (up to about 65 seconds at the default polling and about 80 seconds at 10-second polling); delayed or failed storage can extend that and produces incomplete/unavailable recording status. Storage failures leave live monitoring available. History stays in this Windows profile and is not uploaded or copied by source synchronization. Back up databases only while DeadWare is fully quit.

## Hardware compatibility

DeadWare discovers hardware rather than assuming a particular PC. [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) supplies supported sensor data; Windows counters provide basic fallbacks. Support varies by CPU, GPU, motherboard, laptop firmware, drivers and permissions. Missing sensors are shown as unavailable, and missing history remains a graph gap.

The default hardware scan focuses on CPU and GPU sensors. Extended motherboard, controller, storage and memory-device sensors are optional and off by default, since low-level polling can affect responsiveness on some machines. Open **Settings → Monitoring → Sensor sources** to find **Extended sensors** and **Storage sensors**. Changing **Extended sensors** requires restarting DeadWare. Windows memory usage remains available without extended scanning. Drive temperature and health have their own **Storage sensors** switch in that expander, on by default, read every 30 seconds and applied after a restart; drive throughput and free space do not depend on it. ATA SMART health may need administrator rights. With Extended sensors on, CPU and GPU sensors and the chip that carries the CPU pump header update every poll; other motherboard, memory and controller sensors update every 2 seconds, and drive sensors come from the 30-second storage read (none with Storage sensors off).

CPU temperature on Intel and AMD processors needs DeadWare running as administrator with the PawnIO driver installed. On a laptop or tablet without them, or with an ARM processor such as a Snapdragon Surface, DeadWare shows the temperature from Windows' thermal zones instead: a zone named for the CPU, otherwise the hottest, marked approximate in the status line, with every zone listed on the Sensors page. Desktops are left out, because their boards often report fixed placeholder values.

This first release is **not complete HWiNFO sensor parity**. A successful launch on one PC is not evidence that every sensor works on every device. Please report compatibility findings through the hardware issue template with device models and the capability message, without serial numbers.

## Battery history

Open **Battery history** in the sidebar to see how charge drops and recovers, along with current charging status. The charge line shows Windows energy saver periods (battery saver before Windows 11 24H2): the normal solid line means saver off, dashed amber means saver on, and dotted gray means unknown state. A legend identifies each style. Choose **Open in window** for a separate resizable window; its position, size and Always on top choice are remembered. The Day/Week/Month/Year/All history selector is independent of the live graph range. When Windows reports no battery, the sidebar entry hides automatically; it returns if a battery is detected or its status is unknown. Saved battery history is kept.

The chart grows with the window, and retention and backup notes are under the initially collapsed **Retention and backup** expander in **Keep a lasting record**.

DeadWare records the system battery total once per minute plus observed charging/power and energy saver state changes. On Windows 11 24H2 and later it reads Energy saver's own status, because the older battery-saver flag stays off in Energy saver's standard level; earlier Windows versions keep using that flag. Recording starts automatically on a battery-equipped device and can be paused without deleting saved history. Windows supplies these readings without administrator access. Unknown readings stay unavailable; a desktop with no battery says so. Multiple physical batteries appear as the combined system charge.

Observations are kept indefinitely in `%LOCALAPPDATA%\DeadWare\battery-history.db`, independently of the six-hour live graph cache and Cooling Health retention. There is no automatic expiry or size-based deletion. Storage usage and recording errors appear on the page. The database grows with recorded observations; long-range charts use bounded summaries without deleting originals. Dots show percentage averages and vertical lines show minimum–maximum in each displayed bucket. Hollow charge dots indicate mixed or unknown saver state within a summarized bucket. Green marks identify recorded charging and amber marks identify energy saver; filled marks mean all observations in a bucket reported that state, and outlined marks mean mixed states. They do not establish the state during unobserved time. Missing data, sleep, pauses and restarts remain gaps.

History begins with this version while DeadWare runs; earlier device history cannot be reconstructed. Writes flush every 15 seconds and on normal **Quit DeadWare**. Abrupt power loss can lose the unsaved batch. A storage problem reports an error while the other monitors continue. Resolve storage access and restart to retry. Battery data stays local to this Windows profile; source-code synchronization through GitHub does not copy it to another computer. Export the selected range to a new CSV for a backup, or copy the database while DeadWare is fully quit. Keep your own backup before resetting Windows or deleting the profile. Do not synchronize an open database.

## Usage history

Open **Usage history** in the sidebar, or **Open in window** for a separate resizable window whose position, size and Always on top choice are remembered. Choose **Day**, **Week** or **Month** and use **◀ Earlier** and **Later ▶** to step through past periods. Six charts cover CPU usage, CPU temperature, the dashboard's selected GPU's usage and temperature, RAM usage and network download/upload. Each point is the average of the recorded minutes in its slot, drawn over a shaded minimum–maximum band; minutes without readings stay empty and partial slots are not connected, so sleep, restarts and stopped monitoring remain visible as gaps. The MIN/AVG/MAX line under each chart uses the stored minute values for the whole period, not the drawn slots. Dates use local time.

At page widths of 1,100 DIP or more, the device charts use three columns; narrower pages use two, including in the separate window. Choose **Applications** or **Application resources** in the lower card's tabs; retention details and **Clear history…** are under the initially collapsed **Retention, privacy and clearing** expander in **Keep a longer record**.

The **Applications** table lists per-application download and upload totals for the period, summed by executable name across its processes, with a search box, a traffic strip and an **Other applications** row when more than 200 names were seen. The strip stacks the six applications with the most traffic in the period, plus Other, as average rates over each slot's captured minutes, and its legend gives each one's share; its colours identify applications, not direction. Time without capture is hatched. Totals come from observed ETW traffic, so time without per-application capture is a gap, not zero traffic, and the page says how many recorded minutes had no or incomplete per-application capture; the totals may miss some of their traffic, and the strip leaves them out. Different executables with the same name are combined. **Show in Connections**, after **Clear** in the Applications heading, opens Connections History for the listed slot or the period, showing only the selected application when one is selected. Connections keeps up to 30 days, so earlier minutes are left out, and the button is unavailable for a period that is older.

The **Application resources** tab ranks the apps that used the most CPU time, memory, I/O or GPU in the period, from the history saved while Per-process monitoring is on. Choose **Rank by** CPU time, Average memory, I/O or **GPU**. The table shows each app's CPU time, Avg CPU (its share of all logical processors across every recorded minute of the period, like the live CPU column), Avg memory while listed (private working set, averaged over the minutes the app was listed), I/O read, I/O written, Avg GPU (its busiest GPU engine's share of the time GPU data was recorded), Avg GPU memory while listed (its dedicated GPU memory, averaged over the minutes it was listed with GPU data) and Minutes listed, with a search box, a share bar of the period total and an **Everything else** row; it lists up to 200 apps, and when the period holds more the summary says so, for example "Top 200 of 320 applications". Select an app to chart it across the period in the ranked metric: CPU % of all logical processors, memory, I/O read plus written per second, or, while ranked by GPU, GPU % of the busiest engine. Minutes in which the app was not among the busiest are gaps, not zeros. A notice says how many minutes in the period have no process data (monitoring off, DeadWare not running, or a capture gap); minutes from before the 30 days are not counted, and a period that reaches back that far says they are not kept.

To see what was busy at a moment, click a point on the Device **CPU**, **RAM** or **GPU** chart; on the keyboard, Left and Right move one cursor, shown on all three charts and kept through the minute refresh, Enter lists the point it marks, and Esc or **Clear** clears it. The card lists that slot's busiest apps, ranked by CPU time from the CPU chart, by average memory from the RAM chart and by GPU from the GPU chart, scrolls into view and names the minutes listed in its heading (for example "Busiest apps · 03:13–03:16", with the date on Week and Month); a hairline marks the slot on all three charts. A GPU point needs a GPU selected on the dashboard, since that chart plots only the selected GPU, and ranks the slot by each app's busiest GPU engine on any adapter. **Clear** or Esc returns to the whole period, as do changing the range and **◀ Earlier** or **Later ▶**. A point can stand for several minutes: a Day point is a single minute only when the chart is at least 1,440 pixels wide. A slot recorded while monitoring was off says "No process data in this span.", and a GPU slot with process data but no GPU data says "No GPU data in this span." The Applications traffic strip shares this cursor: moving it on a chart moves the strip's hairline to the same moment. Click a strip slot, or press Enter on the selected one, to list that slot's applications in the Applications table; **Clear** returns it to the whole period.

DeadWare records one row per minute for each metric (average, minimum, maximum, sample count and whether the minute was complete) plus per-application bytes, in `%LOCALAPPDATA%\DeadWare\usage-history.db`. Recording is on by default; **Record usage history on this device** on the page or in Settings pauses it without deleting saved history. Rows are kept for 400 days, and the file is capped at 256 MiB with the oldest whole days dropped first, never the current day; the page shows storage use and the earliest retained minute. GPU rows are keyed by model name, so a change in enumeration order does not split them; two GPUs of the same model are ambiguous and not recorded. A restart inside a minute merges that minute and marks it incomplete. Writes run in the background every 15 seconds and flush on normal Quit; a crash or power loss can lose the unflushed batch. A storage problem reports an error on the page while live monitoring continues.

While **Per-process monitoring** and **Record usage history on this device** are both on, DeadWare saves each minute's busiest apps in `%LOCALAPPDATA%\DeadWare\process-history.db`: the top 10 by CPU time, by memory, by I/O and by GPU, at most 40 apps, plus one Everything else row that holds the rest of the apps the scan saw, unnamed processes included. There is no separate switch; turning either off stops this recording and keeps what was saved until it is 30 days old. Apps are keyed by image name, ignoring case, as on the Processes page. A name that reads as Everything else, or that holds `\`, `/` or `*`, counts in Everything else, and characters that are not valid Unicode are saved as �, so names that differ only there are one app. Minutes are kept for 30 days: older days are removed when DeadWare starts and once a day, also while recording is off, and the card never shows them. The file is capped at 192 MiB with the oldest whole days dropped first, never the current day; a full day at the 40-app cap measured 5.6 MiB, so 30 such days fit. A minute is saved after it ends, so the newest minute appears on the card a minute or so later. Writes run in the background every 15 seconds and flush on normal Quit; a crash or power loss can lose the unflushed minutes. A restart inside a minute keeps that minute's first part and marks it incomplete. A newer, foreign or damaged file is kept and reported, never overwritten, and live monitoring continues. Known limits: usage after the last scan that saw a process is not recorded, nor is a process that starts and exits between two scans, so totals can be lower than the Device charts. CPU time and I/O in a saved minute are always numbers; when an app's counters cannot be compared for one scan, which is rare, that scan counts as 0, so a saved minute can understate an app rather than mark it unknown. Application resource history begins when 0.14.0 first runs with both switches on; earlier versions saved no process data. GPU history begins when 0.15.0 first runs, and earlier minutes have no GPU data. 0.15.0 upgrades the file in place; returning to 0.14.x pauses Application resources history until 0.15 or later is reinstalled, and the file is left as it was.

**Don't record these apps**, under Settings → History and alerts, lists up to 64 apps by executable name, such as chrome.exe. They still show on live pages, marked " · not recorded", but none of their history is saved from then on: no Connections history, no per-app totals in Usage history and no alerts for them. In Application resources their CPU, memory, I/O and GPU count under Everything else, so device totals stay true, and the Device charts still include their traffic. Application traffic budgets for them stop counting. History saved before you add an app is kept until you clear it. Processes that Windows saves as "PID n" can't be matched. **Clear history…**, in the same place, in **Keep a longer record** → **Retention, privacy and clearing** on this page and under Connections' **Location database, recording and storage**, removes saved history for **One app** or **All apps**, **Older than 7 days** (the default: minutes that started more than 7 days before the minute you confirm) or **All time**, after a confirmation that it can't be undone. It clears the chosen apps' records from Connections history, Usage history's per-app totals, Application resources and the alert log's application budget and first-use alerts. Clearing one app moves its Application resources numbers into Everything else; clearing all apps removes those minutes. It keeps device-wide history (CPU, GPU, memory, temperatures, network totals, battery and Cooling Health), other alerts in the log, your alert rules, and the Don't record and Don't alert lists. Rows saved as "PID n" or "Unknown application" are cleared only with **All apps**. **All time** also covers the minute in progress, and the rest of that minute is not saved for the chosen apps, so it can drop up to 60 seconds of new history for them. Connections history hides the cleared history at once; Usage history, Application resources and the alert log can show partly cleared data until they finish, with "Clearing history" in their status lines. A clear runs while recording is paused and needs no administrator rights. Quit, sign-out, Restart as administrator, an update install or a crash interrupts it, and it resumes when DeadWare next starts ("Finishing a clear that was interrupted…"); **Try again** retries a history that failed. A history marked "not cleared", because its clear could not be started or the history was unavailable, needs **Clear history…** again. Freed space is reused for new history; the files don't shrink. Exported CSV files and Windows notification history, which can keep alert balloons that name apps, are not cleared; DeadWare can't reach them, so delete them yourself. On both traffic strips, time cleared for all apps is a **Cleared** band, with "Cleared before …" under the strip, and "Some application history before … was cleared." follows a one-app clear; a recorded slot whose traffic was cleared is hatched as not saved ("No saved traffic"), never drawn as zero. On Connections, an application filter for an app in the list reads **Application: … · not recorded ✕**, with "Not recorded: this app is in Don't record these apps." under the strip, and its recorded slots without saved traffic are hatched the same way.

History begins when version 0.7.0 first runs; the six-hour live graphs and their cache are separate and are not copied into the new store. Year and All ranges are not offered yet. Export the period's device minutes or application totals to a new CSV file; names that look like spreadsheet formulas are neutralized. Application names and byte totals describe what runs on this computer, so treat exports as private. Usage history, including `process-history.db`, stays in this Windows profile and is never uploaded; back up the databases only while DeadWare is fully quit.

## Alerts

Open **Alerts** in the sidebar. **Recent alerts** appears first and grows with the window, with its episode list scrolling inside the card. Below it, **Rules** and **Don't alert** share tabs; **Don't alert** shows the number of apps kept quiet when any are listed. **Rules** lists the thresholds you have set; add one by choosing a kind, a target, a value and a duration, then **Add rule**. Five kinds are available. A **device metric** rule fires when CPU usage, CPU temperature, the dashboard's selected GPU's usage or temperature, or RAM usage is at or above the value for 1, 5, 15 or 60 consecutive recorded minutes. A **network rate** rule does the same for download or upload in MB/s. An **application traffic** rule fires when a named executable's download plus upload reaches a budget in MB within one local calendar day. A **battery** rule fires as soon as the charge is at or below a percentage while running on battery. A **first network use** rule logs each app the first time DeadWare sees it use the network (below). Rules can be edited, switched off without deleting them, or removed.

While you type a threshold, the page shows what Usage history recorded in the last 7 and 30 days: the highest minute, the average and the share of recorded minutes at or above the value. That is the suggestion mechanism; DeadWare never sets a threshold for you.

Every crossing is one **episode**. When it starts, a tray balloon names the rule and the observed value; clicking it opens Alerts. **Recent alerts** lists episodes newest first with their peak and whether they are still open, with **Acknowledge** as a bookkeeping mark and **View in Usage history**, which opens the Day view around the episode so you can see the surrounding minutes. A rule notifies once per episode and re-arms after the metric stays below the threshold minus a small margin (3°C, 5 percentage points or 10% of a byte value) for the rule's duration; it never notifies more than once an hour (first network use is the exception, below), and an application budget notifies once per day. **Show tray notifications for alerts**, on the page and in Settings, mutes balloons for all rules while episodes are still logged. Cooling Health keeps its own warnings and notification setting.

Device and network rules evaluate the per-minute averages that Usage history records, so **Record usage history on this device** must be on for them, and what the log shows is exactly what the Usage history charts show. A minute without a reading neither counts nor resets; a recording gap such as sleep or a restart resets the consecutive count. Application budgets are seeded from the stored day at startup, so a restart mid-day keeps the morning's traffic. Rules are saved in `settings.json`; the log lives in `%LOCALAPPDATA%\DeadWare\alerts.db`, keeps 400 days under a 64 MiB cap, is written in the background and flushed on Quit, and is never uploaded. An alert means a threshold you chose was crossed in observed data; it is not a hardware diagnosis or a security finding.

DeadWare adds one **first network use** rule for you (unless you already have 64 rules, the most it keeps; then remove one and add the rule in the editor); switch it off or remove it like any rule (it has nothing to edit). It needs per-app capture, which runs only while DeadWare runs as administrator, and waits until that has run once. It then learns quietly for three calendar days (the day capture first ran and the next two, ending at local midnight). The days count whether or not DeadWare runs as administrator during them, so the fewer apps it sees then, the more alert afterwards. Every app already in Usage history or Connections history counts as known. After that, the first time an app DeadWare does not know sends or receives traffic, one episode names it. Apps seen within 60 seconds of the first share one tray balloon, shown when that minute ends; unlike other rules these balloons are not limited to one an hour, but there is at most one a minute. Each app alerts once. **Don't alert for this app** on its log row keeps it quiet if it ever counts as new again, such as after **Clear history…**; **Alert again** in the **Don't alert** tab undoes that. Apps are told apart only by executable name, so a different program called chrome.exe counts as known, and a program whose file name changes with each build or install counts as new each time. Loopback traffic (127.0.0.0/8 and ::1) is not network use; traffic to this PC's own network address is. Apps in **Don't record these apps** and processes DeadWare can name only by PID, such as Windows' System process, are never learned or alerted; an app you take off that list is new unless DeadWare knew it before you added it. Clearing an app's history for all time removes it from the known list, so its next use alerts again, at its next poll if it is running. Clearing all apps for all time empties the known list without a new learning period, so each app alerts once at its next use, one balloon a minute. Clearing older than 7 days keeps every app known. The Don't alert list stays. An app unseen for 400 days is forgotten, and when 8,192 apps are known the one seen least recently is forgotten to make room. The rule works whether or not Usage or Connections recording is on. Switching it off keeps learning quietly. Removing it stops learning and keeps the list, so if you add it back later, each app first used meanwhile alerts once at its next use.

A first network use row in **Recent alerts** has **View in Connections**, which opens Connections History from 5 minutes before to 10 minutes after that minute, showing only that app, while Connections still keeps the minute (30 days), and **View in Usage history** after that. **Don't record these apps** and **Clear history…** ([Usage history](#usage-history)) also apply to alerts: application traffic budgets of apps in the list stop counting, clearing an app's history for all time makes its next network use alert again, and clearing older than 7 days keeps it known.

## Cooling Health

The **Cooling Health** page saves local CPU/GPU temperature, usage and package power, plus clock and fan readings when supported. A GPU's fan speed comes from the card. A single CPU's fan speed comes from its cooler: a motherboard or AIO header labeled as a pump (for example `Pump Fan` or `AIO Pump`), otherwise the `CPU Fan` header. These readings need **Extended sensors**; unlabeled headers such as `Fan #2` are not used. Turning Extended sensors on or off changes the CPU sensor mapping, so its Cooling Health history and references start under a new identity. Recording starts by default; optional tray notifications start off. Choose a device and day/week/month range, switch metrics or export a new CSV file. Settings and the SQLite history database live under `%LOCALAPPDATA%\DeadWare`. No thermal data is uploaded. Per-application network data is not stored there.

The thermal history chart grows with the available page height, with Cooling assessment beside it on wide windows and above it on narrower windows. The lower card has **Reference**, **Warnings** and **Recording & setup** tabs; open the initially collapsed **Save a new reference** editor on Reference to save a reference period.

The first minute produces a history window. To compare cooling, select a past period of up to seven days when you believe the setup was operating normally and save it as a named reference. At least 30 eligible minute windows are needed. The first five minutes, gaps, unstable workloads, missing required readings and known throttling are excluded; learning can therefore take longer than 35 minutes. Saved reference readings stay fixed rather than learning a developing problem as normal.

Comparisons need ten consecutive stable recent minutes, each matched to at least ten reference windows within 10% or 5 W of package power (whichever is larger), ten percentage points of load, and comparable fan speed when both sides provide it. The initial warning rule requires every recent minute to exceed the reference mean by at least 5°C and its 95th percentile by at least 3°C. These conservative engineering defaults are not validated probabilities of hardware failure. Cooling Health does not use coolant or room temperature in its comparison; the Corsair hub's coolant reading, while DeadWare drives the hub, is shown elsewhere ([The Corsair hub](#the-corsair-hub)). Fan context may also be unavailable. Temperature-target boosting can conceal cooling deterioration, so an ordinary comparison is not a health certificate.

Warnings are logged even when tray notifications are muted. Enable notifications if desired; warnings can be acknowledged and are limited to one per device/reference per 24 hours. An unacknowledged warning suppresses repeats. Changing the active reference does not modify its saved readings. Choose **New cooling setup** after hardware replacement (including a replacement with the same model), cleaning, remounting, fan-curve or power-limit changes. Local identity uses machine, hardware metadata and the selected sensor mapping; it cannot identify every physical replacement automatically. When multiple devices have identical model names, their histories are separated by session and comparison is disabled because enumeration cannot establish physical identity. Older setups remain available for history viewing.

By default, minute detail is retained for 30 days and hourly summaries for 90 days. Controls offer 7/30 days of detail and 30/90 days of summaries. The database is capped at 256 MiB with a bounded journal; the page shows storage usage. Up to ten references per device/setup are retained. If storage is locked, full or corrupt, recording reports an error and live monitoring continues; resolve the storage issue and restart to retry. Saved references can consume space independently of ordinary history retention. Database files are local to this Windows profile; cloud synchronization of an open database is not supported.

Cooling Health flags changes worth investigating. It cannot diagnose a blocked cooler, failing pump, or remaining lifespan. Pump speed is recorded as CPU fan context when a labeled pump header is available, but RPM alone cannot show flow, and flow is not measured. Cooling Health does not use coolant temperature either, and it keeps the sensor it has always used for the pump, never the hub's. While DeadWare drives a Corsair hub, the hub's coolant reading is on the hub's card on the **Lighting** page, on the Sensors page and, if you tick it, as a line on the CPU temperature graphs ([The Corsair hub](#the-corsair-hub)).

## Lighting

Open **Lighting** in the sidebar, below Cooling Health, to set your PC's RGB lights. DeadWare drives them through [OpenRGB](https://openrgb.org/), which you install yourself: it isn't included with DeadWare, and DeadWare is tested with OpenRGB 1.0rc3. Lighting is off until you turn it on. In **Settings → Lighting**, choose **Browse…** under **OpenRGB location** and pick `OpenRGB.exe` (any other file is refused), then turn on **Enable lighting**, which stays unavailable until OpenRGB is chosen. DeadWare then starts its lighting helper, `DeadWare.Devices.exe` in DeadWare's folder, a background program without a window. The helper starts OpenRGB with its SDK server on port 6744, which listens only on this PC (other computers on your network can't reach it), connects to it and keeps the lights going. OpenRGB doesn't check who connects, so while DeadWare runs as administrator, only its lighting helper can connect to the OpenRGB it starts: other programs, other RGB apps included, can't use it. DeadWare has Windows refuse their connections for as long as the helper runs, nothing of that is kept after it ends, and if Windows won't refuse them the helper doesn't start OpenRGB and the Lighting page says why. It also doesn't start it if its own test connection, made just before, shows that the limit would block the helper too, or that another program already uses port 6744. Without administrator rights DeadWare doesn't limit the port, so any program on this PC, whoever runs it, can control that OpenRGB with your rights. Until you change them, lighting starts with **Lights on** turned on, **Brightness** at 100% and one shared colour, DeadLight's steel blue (`#4682B4`), on every zone DeadWare colours; devices that were running effects of their own, such as a rainbow on RAM, stop them as soon as DeadWare sets their colours. Choosing another OpenRGB while lighting is on restarts lighting with it, never sooner than 4 seconds after the previous helper stopped, and turning **Enable lighting** off stops the helper and its OpenRGB, except when the helper has administrator rights and DeadWare doesn't (see the next paragraph). With lighting on, the helper starts with DeadWare; when **Start with Windows** starts DeadWare at sign-in, the helper waits about 10 seconds before starting OpenRGB, so USB devices can settle.

When DeadWare runs as administrator, the lighting helper and OpenRGB do too, so keep OpenRGB in a folder that only administrators can change: copy the whole OpenRGB folder to `C:\Program Files\OpenRGB`, which needs administrator approval, and choose `OpenRGB.exe` there. Settings warns when programs running without administrator rights can change the folder you chose, such as one in Downloads, and recommends that move; a folder it can't check, such as one reached through a link or junction or one on a network drive, is reported with the reason and the same recommendation. While DeadWare runs as administrator, the helper won't run OpenRGB from such a folder at all, nor from one it can't check: the Lighting page and Settings say which (Settings then shows the helper's message instead of its own line about the folder), and lighting starts once you choose an `OpenRGB.exe` in a folder only administrators can change. RAM, motherboard and graphics-card lighting need DeadWare to run as administrator, because OpenRGB reaches many of those devices only with administrator rights. Without them those devices can be missing, and the Lighting page says "Restart as administrator for RAM, motherboard and GPU lighting". **Restart as administrator** restarts the lighting helper and OpenRGB with administrator rights as well. A DeadWare running without administrator rights can't control a lighting helper that has them, such as one left running after a DeadWare running as administrator crashed or was ended, and says to restart DeadWare as administrator. Nor can it stop that helper: the helper and its OpenRGB keep running through **Quit DeadWare**, turning **Enable lighting** off or choosing another OpenRGB, and **Update & restart** and **Roll back & restart** then stop without replacing files. To stop that helper, restart DeadWare as administrator, then turn **Enable lighting** off. If it is already off there, turn it on first, which connects DeadWare to the helper (until then **Conflicts** lists the helper's OpenRGB as another OpenRGB), then turn it off again. **Quit DeadWare** also stops the helper once DeadWare is connected to it, but leaves **Enable lighting** on for the next start.

Two programs driving the same lights make them flicker, so the lighting helper doesn't start OpenRGB while a program that blocks lighting is running, and the Lighting page and the **Conflicts** list in **Settings → Lighting** say which. These block lighting:

- DeadLight, the separate lighting app this replaces. Quit it from its tray icon.
- Another OpenRGB, one the running lighting helper didn't start. Quit an OpenRGB you started yourself from its window or tray icon. The OpenRGB a lighting helper starts ends with that helper, even when the helper crashes or is ended in Task Manager. An earlier helper's OpenRGB can be left behind in two rare cases: Windows refused to tie the two together, which the helper's log records, or the helper ended in the moment between starting OpenRGB and tying it. That OpenRGB has no window or tray icon, so end `OpenRGB.exe` in Task Manager, or restart Windows.
- iCUE, `iCUE.exe` or `iCUE Launcher.exe`. Quit it from its tray icon.
- The Corsair device services, `CorsairDeviceControlService.exe` and `CorsairDeviceListerService.exe`. Stop them in Windows Services, or quit iCUE completely.

Quitting a program or stopping a service lasts only until it starts again. A program set to start when you sign in, such as iCUE through its startup entry or DeadLight through its task in Task Scheduler, starts again at your next sign-in, and a service whose startup type is Automatic starts again with Windows. To keep them from starting by themselves, turn off iCUE's entry in **Task Manager → Startup apps** and DeadLight's task in Task Scheduler, and set the Corsair device services' **Startup type** to Manual in Windows Services. DeadWare only reports these programs; it never changes another program's services or startup entries.

**Conflicts** also lists the Corsair service, `Corsair.Service.exe`, which doesn't block lighting. With **DeadWare drives the hub** turned on (see [The Corsair hub](#the-corsair-hub)), it does make DeadWare let go of the hub, and it blocks the take-over. The helper checks every 5 seconds and starts lighting by itself once nothing blocks it. If a program that blocks lighting starts while lighting runs, the helper stops its OpenRGB until that program has gone, then starts it again at the pace it uses after OpenRGB stops unexpectedly, and these stops count towards giving up (both described below). With lighting off, Settings checks for these programs itself whenever its Lighting tab comes into view.

A Corsair iCUE LINK System Hub has one mode for its lights and its cooling. While lighting is on and **DeadWare drives the hub** is off, which is how it starts, OpenRGB holds the whole hub, out of the hub's own built-in mode, so that it can set the hub's colours. DeadWare sets no fan or pump speeds, in either case, and nobody has yet checked what the hub's fans and pump do while a program holds the hub this way without setting their speeds. With the switch on, **Quit DeadWare**, turning **Enable lighting** off, **Update & restart** and **Roll back & restart** hand the hub back before anything else stops: it returns to its own stored lights and fan settings. With the switch off, as before, nothing hands the hub back: those stops end OpenRGB and DeadWare doesn't touch the hub. [The Corsair hub](#the-corsair-hub) has the rest.

While lighting is off, the Lighting page says so, and **Open Settings** opens Settings. With lighting on, the page header holds **Lights on** and **Brightness** (0–100%), and a status line under it says what the lighting helper is doing or what stops it: connecting or starting, waiting for OpenRGB, a program that blocks lighting, OpenRGB missing or failing, a change that didn't apply, and the administrator note. Under it, four tiles choose the effect: **Static** (your saved colours), **Wave** (sweeps across the desk), **Breathing** (everything pulses together) and **Spectrum** (cycles through colours together). Clicking a tile starts that effect at once, with no Apply button, and the chosen effect's settings show under the tiles; each effect keeps its own settings while another is chosen. With **Static** chosen, the lights show your saved colours, and **Set all colours** opens a colour picker whose colour goes to every zone and clears the zones' own colours; the dot on the button shows that shared colour, and while the picker is open, **Undo** puts back the colours from when you opened it. Turning **Lights on** off turns DeadWare's lights black, whatever the effect, and **Brightness** scales the colours DeadWare sets, an effect's included.

**Wave** sends colour across the desk, in the order the desk drawing (below) puts your devices in. Its settings are **Colours**, **Speed**, **Direction** and **Spread**. **Colours** holds up to 8 colours. **Add colour** adds one, red for the first and a copy of the last one after that, and is hidden once there are 8; click a colour to change it in a picker, where **Remove** takes it out. The colours blend into each other along the wave, the last back into the first, and a single colour lights everything in that colour. With no colours chosen, the page says "No colours chosen: the wave uses the full rainbow." and the wave runs through the whole rainbow. **Speed** goes from 0 to 100 and starts at 40: at 0 one cycle takes 20 seconds, at 100 there are two a second. **Direction** is one of eight: **Left to right** (the one to start with), **Right to left**, **Back to front**, **Front to back**, **Back-left to front-right**, **Back-right to front-left**, **Front-right to back-left** and **Front-left to back-right**, where the back is the far side of the desk and the front is your seat. **Spread** goes from 0 to 100 and starts at 50; higher makes the colour bands narrower, so more of them fit across the desk. **Breathing** pulses every light together, from black up to its colour and back: each zone's own colour, or the shared colour for a zone without one. **Spectrum** takes every light together round the full colour circle. Both have **Speed** alone. Every light in a zone shows the zone's colour, so a keyboard that OpenRGB lists as one zone shows one colour across all its keys at any moment as the wave passes over it. Choosing an effect can take up to about half a second to start moving.

The **Desk** card under the tiles depends on the PC. DeadWare has one built-in picture, for a PC with an MSI MAG B650M MORTAR WIFI motherboard (`MSI MAG B650M MORTAR WIFI (MS-7D76)`) and a Corsair iCUE LINK System Hub (`Corsair iCUE Link System Hub`). When the lighting helper finds both, the card shows that picture, described next. Once the picture has been saved it stays, whatever devices are found later: OpenRGB lists devices a few at a time after each start, so a part can be missing for a while. Every other PC gets the plain desk, described after the picture, and has no inside view. While the helper is still finding devices, a PC without a saved picture shows "Looking for lighting devices…" in place of the card until the first device or the picture appears, and a PC that has saved the picture shows it, dimmed, with its parts marked "not found" until the helper runs and finds them.

The picture has two views, drawn at a fixed shape that grows with the window up to 1280 px wide. The desk view, titled **Desk**, draws the desk from above with the keyboard, the mouse and the PC tower, each lit part in its own colour with a soft glow, and says "tap a device to change its colours · tap the PC to see inside". Tap the PC tower, which is labelled "tap to see inside ↗", to open the inside view, titled **Inside the PC**: a side window of the case with the rear on the left and the front on the right, holding radiator fans 1 to 3, the pump, RAM 1 and RAM 2, the graphics card and the front fans. **← Back to desk** returns to the desk view. A part runs its own effect when its device does, as the front fans do on the Lighting Node Pro; it is drawn grey and the inside view says "own effect" under the front fans. A part whose device isn't found is drawn as an outline marked "not found" and can't be tapped. With **Lights on** off every part is drawn unlit, and while the lighting helper isn't running the picture is dimmed and taps do nothing. Under the picture, "Not in the picture:" lists any lit device the picture has no part for, with its number of zones, such as "MSI motherboard headers" followed by its number of zones, and any device in the picture that has lit zones no part covers, with the number of those zones, and says these keep your saved colour during effects.

The colour card sits beside the picture on a window 1040 px wide or more, and under it on a narrower one. It reads "Nothing selected" until you tap a device or a part, with "Tap a device in the picture to change its colours." in the desk view and "Tap a part to change its colours." inside. Tap a part to select it: its device's card shows, with a swatch for each zone that opens the same colour picker as on the plain desk, and its rows are named after the parts, such as "RAM 1", "Radiator fan 2" and "Pump". A device with one part in the picture heads its card with the part and the device, such as "Keyboard · SteelSeries Apex Pro", and says where it is selected; a device with several parts, such as the hub, heads it with the device's name and the selected part, such as "radiator fan 2 selected". Either way the row of the zone the part shows is highlighted: the keyboard's one row, "Middle" for the mouse, "GPU zone 1" for the graphics card, and the selected part's own row on the hub. A tap on empty space clears the selection. Opening a view, or leaving the page and coming back, clears it too.

The picture is one stop for the keyboard. Press Tab to reach it; the arrow keys then move through the found parts of the view, in the picture's own order: keyboard, mouse and then the PC tower in the desk view; radiator fans 1 to 3, the pump, RAM 1 and 2, the graphics card and the three front fans inside. An arrow key selects a part as a tap does. Press Enter or Space on the PC tower to open the inside view, and Escape in the inside view to go back to the desk. While the lighting helper isn't running, the arrow keys do nothing, as taps do nothing.

On a PC with the picture, the Wave runs over the picture's own places: each zone takes the point of its part, and the parts inside the PC are spread over the tower's place on the desk as they sit in the case, so a **Left to right** wave crosses the PC from the rear to the front. In the desk view, while Wave runs with **Lights on**, a soft band across the middle and an arrow with a caption such as "wave moving left to right" show the way the wave travels. In the settings under the tiles, **Colours**, **Speed**, **Direction** and **Spread** sit on one row, going on to another line only where the window is too narrow for them.

A PC with the picture can't rearrange its layout. **Edit layout**, the **Devices** list and **Not placed** aren't shown, and the lighting helper refuses a change to the layout with "This PC's layout comes from its built-in picture." The next three paragraphs, on the plain desk, the **Devices** list and arranging devices, are for any other PC.

On any other PC the card draws your desk from above, "BACK OF DESK" at the top and "FRONT · YOUR SEAT" at the bottom: the desk's outline, a box for each lit device on the desk with its name and its number of zones, drawn in its zones' colours (their average when they differ), and a dashed box for the PC tower, labelled with the number of devices inside it, such as "PC tower · 3 devices". The outline is only a guide, and effects don't use it. Click a device to select it; its panel shows beside the desk, or under it on a narrow window. Click the closed tower anywhere, its label included, to open it and select it: its box grows to take in the devices inside it, drawn as boxes of their own, and the tower's panel says how many devices it holds. On the open tower, a click on the label closes it again and a click elsewhere on its box selects the tower; selecting a device inside the closed tower opens it; and a click on empty desk clears the selection. A device running its own effect is drawn grey and tagged "own effect". While the lighting helper isn't running, the desk stays as it was, dimmed, and clicks on it do nothing; with **Lights on** off, the boxes are drawn unlit.

The **Devices** card under the desk lists every device, and is the way to select one with the keyboard or a screen reader, which can't read the drawing. Each row's second line says where the device is: "On desk"; "Inside PC", in the PC tower; "Own effect", running an effect of its own (see below); "Not placed", taken off the desk; or "Not on desk", a device DeadWare can't light or one without a zone that has LEDs, which the desk never draws. A device running its own effect still reads "Own effect" in the list after you take it off the desk. Every device you took off the desk is also listed under **Not placed**, each with **Place on desk**, which puts it back on the desk wherever DeadWare finds room, as for a new device. The panel shows the selected device's name and zones, or "Select a device on the desk or in the list." with nothing selected. A device DeadWare colours lists its zones, each marked "Own colour" or "Shared colour": click a zone's swatch to give it a colour of its own, or choose **Use the shared colour** there to return it to the shared one. A zone without LEDs has no swatch, a device without a Direct mode in OpenRGB reads "DeadWare can't drive this device", and one without zones reads "This device has no colour zones." Colours go to the lights only while the helper is running; until then the desk, the list and the panel stay as they were, unavailable.

A device card, whether it comes from the picture, the desk or the **Devices** list, has up to three sections under its zone rows, each under a line of its own. **Lighting mode** shows only on a keyboard's card, and on the card of a device that still has a saved mode, as explained below; a mouse, fan or RAM card has the other two. They go to the lights only while the lighting helper is running; until then they are unavailable and show what they showed. A device DeadWare can't drive has none of them.

- **Lighting mode** is for keyboards. **Follow the desk effect**, the default, leaves the keyboard on the desk's effect, as before. The other four give that keyboard a mode of its own, whatever effect the desk runs: **Static** holds each zone's colour; **Breathing** pulses each zone's colour; **Colour cycle** moves every light together round the full colour circle; **Rainbow wave** sends a rainbow across the keyboard from left to right, by where each key sits. **Speed** sets how fast the last three move, and is hidden for Static and Follow the desk effect. **Rainbow wave** can only be chosen when the keyboard reports where its keys are; otherwise it is greyed out and the card says "This keyboard doesn't report its key positions." With **Lights on** off, a keyboard in a mode is dark.
- **Brightness**, the **This device** slider, runs from 0 to 100%. It works with the page's **Brightness**, so the two are multiplied: a device at 50% on a page at 80% shows 40%, and the card says "Works with the page's Brightness: 50% of 80% here." while either is below 100%.
- **Colour correction** has a **Red**, **Green** and **Blue** slider, each from 0 to 200, where 100 means the colour is left as it is. It is for a device whose white looks tinted next to your others: take a little off the channel that is too strong, or add to the weak one. **Reset** puts all three back to 100 and is available while any of them isn't. A device with more than one part in the picture, such as the hub, says that brightness and colour correction apply to the whole device and names its parts.

With every slider at its starting value, 100% brightness, correction 100 and no mode, the lights are exactly as they were before these sections existed. Your choices are saved with your other lighting choices.

A device running an effect of its own, such as the Lighting Node Pro, shows the same sections greyed out under a note that begins with its own effect: DeadWare's colours, brightness and colour correction don't reach it while it does. Its tuning is kept, and takes effect again when the device stops running its own effect. A keyboard whose saved mode it can't run, such as Rainbow wave on a keyboard that doesn't report key positions, is lit as **Static** meanwhile; the card keeps showing the saved mode, with the reason under it. The same goes for a saved mode on a device that isn't a keyboard: its card shows the mode and "Lighting modes are for keyboards.", it is lit as **Static**, and the other modes are listed but greyed out, so **Follow the desk effect** is the only one that can be picked, and it clears the mode.

On a PC with the picture, a keyboard that reports where its keys are is drawn key by key, each key in the colour it has now, so a mode or the desk's effect can be watched moving across it; a keyboard that doesn't is drawn with four plain lines, as before. The picture shows the colours as intended, before a device's **Brightness**, its colour correction and the page's **Brightness**: it doesn't dim or tint with the sliders, though the lights themselves do. If you go back to 0.19.0 after tuning a device, 0.19.0 runs the lights but won't save lighting changes; your tuning is there again when you update.

### Painting keys, layers and saved looks

A keyboard's card has three more parts: **Saved looks**, **Key colours** (it says how many keys are painted, with a **Paint keys…** button) and **Layers** (it says how many layers there are, or "No layers", with an **Edit layers…** button). From the top, a keyboard's card reads: **Saved looks**, its zone rows, **Key colours**, **Lighting mode**, **Layers**, **Brightness** and **Colour correction**. **Lighting mode**, **Brightness** and **Colour correction** are as before. These parts need the keyboard to report where its keys are and what they are called. If it doesn't, **Paint keys…** and **Edit layers…** are greyed out, with "This keyboard doesn't report its key positions." or "This keyboard doesn't report its keys' names." A keyboard running an effect of its own has them greyed out too.

**Paint keys…** and **Edit layers…** open a large drawing of the keyboard, in place of the desk picture. They work only while the Lighting page shows the built-in desk picture; on the plain desk they are greyed out, with "Painting keys and layers need the desk picture, which this PC doesn't have yet." under each. A two-part switch at the top, **Key colours** and **Layers**, moves between the two; **Done** goes back to the desk. Changing to another device, or leaving the Lighting page, closes the large view as **Done** does. Every change goes to the keyboard and is saved as you make it. Each key is drawn in the colour it has now.

**Key colours.** Click a key to pick it, and click it again to drop it. Drag across keys to pick several; if the drag starts on a picked key, it drops them instead. The groups **All**, **None**, **WASD**, **Arrows**, **Number row**, **F keys** and **Number pad** pick in one click (a group the keyboard has no key for isn't shown). Choose a colour, from the picker or a swatch, and the picked keys take it. **Remove paint** has two choices, **From the picked keys** and **From every key**. A key you haven't painted shows what the lighting mode gives it. **Undo** steps back through the colour changes since you opened the view, up to the last 50: it covers key colours only, and it is forgotten when you press **Done** or change look. To give a look one colour all over, pick **All** and paint.

**Layers.** A layer goes on top of the keys' colours. Press **+ Add a layer** (you can have up to 8). Each row of the list reads kind and which keys, with buttons to move it up or down and to remove it. Lower in the list is on top. A layer is one of four kinds, under **What it does**:

- **A colour** lays one colour over the keys you choose.
- **An effect** puts a moving effect (**Wave**, **Breathing** or **Spectrum**, with its **Speed**) over the keys you choose.
- **Key fade** lights a key when you press it, then fades it out.
- **Key ripple** sends a ring of light out from the key you press.

**Colour** is not offered for the effects **Wave** and **Spectrum**. **How long it lasts** (for a key fade or key ripple) runs from 0.1 to 3.0 seconds, and starts at 0.6. **Strength** runs from 0 to 100%. **How it mixes with what's under it** is **Covers it**, which replaces what is below in proportion to the strength, or **Adds light to it**, which adds the layer's light to what is below. **Which keys** is **All keys** or **Only the keys I pick**; for the second, **Pick keys…** turns the large drawing into the key picker, with the same clicks, drag and groups as **Key colours**, until you press **Finished picking**. A new layer is a **Key fade**, light blue, 0.6 seconds, strength 100%, adding light, on all keys, so that adding one never blanks the keyboard. Each layer works on the picture the layers before it left, and the colour is rounded to the lights' whole numbers only once, at the end. If the keyboard's keys change so that a painted key or a layer's key no longer matches, DeadWare skips it, says how many on the card, and keeps it.

**Key presses.** While any layer is a **Key fade** or **Key ripple**, the card shows this note:

> **Key fade and key ripple need DeadWare to notice key presses.** It learns only which light to flash. It never stores what you type and sends it nowhere outside DeadWare, and it stops noticing as soon as no layer needs it. While this page is open, the keyboard drawn here lights up with your presses too.
>
> A press on any keyboard plugged into this PC lights this one: Windows doesn't say which keyboard a key came from.

In more detail: the lighting helper notices a key going down or up through one Windows keyboard hook, and reads only which key it was (its scan code), whether it is one of the keys Windows marks as extended (such as the arrows and the right-hand Ctrl and Alt), whether software sent it, and whether it went down or up. It never reads what character the key types. A key that software sent, which is how programs type text, is ignored outright, so it gives no reaction. A key held down gives one reaction, not a stream. DeadWare passes every key on untouched and never changes or blocks one. The hook is there only while the lights are on, DeadWare is driving a keyboard's lights itself (not leaving it on an effect of its own), and that keyboard has a **Key fade** or **Key ripple** layer that could do something, and it is taken away as soon as that stops being so. To make sure Windows hasn't quietly taken it away, the helper puts it back every five minutes while it is needed. For up to three seconds, and for at most 32 presses, the helper remembers which lights were just pressed, so it can draw the fade or ring, and which keys are held down at that moment (a key not seen for two seconds is forgotten); it keeps nothing longer, writes none of it to a file, a log or the settings, and sends none of it anywhere. The one place it goes is the picture on this page: the colours a press causes are in the frames the helper sends the Lighting page while it shows, over the helper's own pipe, so the large keyboard lights up with your presses. Any keyboard plugged into this PC lights this one, because Windows doesn't say which keyboard a key came from. If DeadWare isn't running as administrator, Windows doesn't give the helper keys typed into a window that is, so reactions pause while an administrator window is in front.

**Saved looks.** A look is a named copy of the keyboard's painted keys, its lighting mode (with its **Speed**) and its layers. It doesn't keep **Brightness**, **Colour correction** or the zones' colours, which tune the lights rather than the look. **Save as a new look…** asks for a name, 1 to 40 characters, and saves the keyboard as it is; a name already used (capital letters don't count) is refused with "There is already a look called" and the name. A keyboard holds up to 12 looks. Choosing a look in the drop-down puts the keyboard to it. If the keyboard has changes that are in no look, the page first asks "The keyboard's current setup isn't saved in a look. Switch and lose it?", with **Switch** and **Cancel**. After a look's name the drop-down says **(changed)** when the keyboard no longer matches it; **Save changes** then replaces the look with the keyboard as it is. **Rename** and **Delete** act on the look shown; **Delete** asks first, and doesn't change the keyboard's lights. With no looks saved, only **Save as a new look…** shows.

**Going back.** An older DeadWare than 0.21.0, given a `lighting.json` that has painted keys, layers or looks, runs the lights without them (no painted keys, no layers, no looks) and won't save lighting changes, so it leaves them in the file; everything is back when 0.21.0 runs again. With nothing painted, no layers and no looks, the file and the colours are exactly as in 0.20.0.

You don't have to arrange anything for effects to work. The lighting helper checks OpenRGB's devices every 5 seconds and gives a device it hasn't placed before a place on the desk. A device whose name says keyboard, keypad, mouse, mouse pad (`mousepad` or `mousemat`) or headset, or Apex, Aerox, Arctis, Rival or DeathAdder, goes along the front of the desk; any other device goes inside the PC tower. An unplugged device keeps its place for when it comes back. To put devices where they really are, click **Edit layout** on the desk card; it reads **Done** while it is on, and leaving the Lighting page turns it off. Drag a device's box to move it, all its zones together, and drag the tower by its label, or anywhere on it while it is closed, to move it with every device inside it. Drop a device on the tower's box to put it inside; drop a device from inside the tower outside it to take it out, and DeadWare then leaves it out. Positions snap to a grid of 48 by 48 steps. The lights take a device's new place when you drop it, not while you drag it. With a device or the tower selected, the arrow keys move it one grid step, Up towards the back of the desk, while the desk has the keyboard focus: click the device, or press Tab until the desk is focused. In Edit layout the panel of a device on the desk or in the tower also has **Inside PC tower**, which puts the device in the tower or takes it out, as dragging does; **Move zones separately**, which draws each of the device's zones as a labelled dot of its own that you drag on its own, for a device whose zones sit in different places, and isn't saved; and **Take off the desk**, which moves the device to **Not placed**. **Desk shape** chooses the outline, **Straight**, **L left** (the one to start with) or **L right**, and changes nothing else. **Reset positions** asks "Arrange every device from scratch? The desk shape is kept." and, with **Reset**, places every connected device afresh as if it were new: devices you took off the desk or out of the tower can go back, and the places kept for unplugged devices are forgotten.

Effects run in the lighting helper, so they keep going while DeadWare's window is closed to the tray or hidden, and if it crashes. A device running its own effect, such as Corsair's Lighting Node Pro (next paragraph), keeps that effect whichever effect you choose. A device you took off the desk keeps its saved colour, its own or the shared one, during every effect. While the Lighting page is showing and an effect runs, the desk shows the colours the lights are taking, up to 10 times a second; the drawing doesn't follow them while another page is showing or the window is closed, and picks them up again when you come back. They are the colours before **Brightness** is applied, so the drawing stays readable at low brightness.

DeadWare doesn't put its colours on Corsair's Lighting Node Pro, because OpenRGB's direct colours have shown only partly or strobed on it. Instead it switches the Node Pro to its built-in **Rainbow Wave** effect, whatever effect it was running before. The Node Pro's panel names its own effect and says DeadWare's colours don't show on it, and it lists no zones or colours: **Set all colours** still sets the shared colour, which simply doesn't show on the Node Pro, and **Brightness** doesn't change it. When **Lights on** is off, DeadWare sets it to its Static mode in black if it has one; otherwise it keeps running Rainbow Wave, and its panel says, whether the lights are on or off, that it stays lit when lights are off.

Closing the dashboard to the tray keeps lighting running. **Quit DeadWare** stops the lighting helper and the OpenRGB it started: it asks the helper to stop, and ends both if the helper hasn't stopped within 5 seconds. A DeadWare without administrator rights can't stop a helper that has them, as described above. Quitting doesn't turn the lights off first; what each device shows once OpenRGB has stopped depends on the device. If DeadWare's window crashes or is ended, the helper keeps the lights going, and the next DeadWare start reconnects to it, unless the helper has administrator rights and that DeadWare doesn't (see above). If the helper stops unexpectedly, DeadWare starts it again after 4 seconds, waiting longer after each further stop, and after 5 stops in 10 minutes it gives up and says so; turning lighting off and on in Settings tries again. The helper restarts OpenRGB the same way. If the helper crashes or is ended in Task Manager, Windows ends the OpenRGB it started along with it, so the restarted helper starts OpenRGB afresh; in the two rare cases described above under another OpenRGB, that OpenRGB is left behind instead. **Update & restart** and **Roll back & restart** stop the helper as Quit does, and the updater waits up to 10 seconds for it to exit before replacing any file; if it is still running, the update stops without replacing files and DeadWare starts again as it was.

The helper saves your lighting choices in `%LOCALAPPDATA%\DeadWare\lighting.json`; a damaged file, which includes any file over 1 MiB, is set aside beside it as `lighting.corrupt-….json`, and lighting starts with defaults. A change that would make the file larger than 1 MiB isn't made, and the Lighting page says why. A file saved by a newer DeadWare, for example before **Roll back & restart**, is never rewritten: it is used if this version accepts every value in it, lighting uses its defaults if not, and the Lighting page says which. One this version can't read at all, because a setting it knows has changed form, is set aside as damaged instead, and your next change writes a fresh file. OpenRGB keeps its settings for DeadWare apart from those of an OpenRGB you run yourself: in `%ProgramData%\DeadWare\openrgb`, which only administrators can change, when DeadWare runs as administrator, and in `%LOCALAPPDATA%\DeadWare\openrgb` otherwise. OpenRGB's own log for DeadWare is in the `logs` folder inside that settings folder, not in your own `%APPDATA%\OpenRGB`; OpenRGB keeps its two newest logs there: the run in progress and the one before it. Settings you made in another copy of OpenRGB, such as the sizes of addressable (ARGB) zones or devices you told it not to detect, therefore don't carry over to DeadWare's; a resizable zone that DeadWare's OpenRGB has no size for can have no LEDs, and then has no swatch. DeadWare sizes one zone itself, as DeadLight does: when Corsair's Lighting Node Pro reports no LEDs on its channel 1, a size of 0 set by hand included, DeadWare sets it to 48, the three LL fans' LEDs, so that Rainbow Wave has LEDs to run on; it never touches channel 2. DeadWare checks this when it connects to OpenRGB and every 5 seconds after that, until one sizing holds, while DeadLight checks it every half second or more often, for as long as it runs. To size another resizable zone for DeadWare's OpenRGB, turn **Enable lighting** off, then, once lighting has run as administrator and made that folder, run `set "APPDATA=%ProgramData%\DeadWare" & set "PATH=%SystemRoot%\System32;%SystemRoot%" & set "QT_PLUGIN_PATH=" & set "QT_QPA_PLATFORM_PLUGIN_PATH=" & "C:\Program Files\OpenRGB\OpenRGB.exe" --config "%ProgramData%\DeadWare\openrgb"` from a Command Prompt run as administrator (when DeadWare doesn't run as administrator, run `set "APPDATA=%LOCALAPPDATA%\DeadWare" & set "PATH=%SystemRoot%\System32;%SystemRoot%" & set "QT_PLUGIN_PATH=" & set "QT_QPA_PLATFORM_PLUGIN_PATH=" & "C:\Program Files\OpenRGB\OpenRGB.exe" --config "%LOCALAPPDATA%\DeadWare\openrgb"` from an ordinary Command Prompt). The `set` commands give that OpenRGB the helper's settings folder and a search path of only the Windows system folders, and clear the two variables that would tell it where to look for Qt plugins, so it doesn't read settings or keep its log in your own `%APPDATA%`, and doesn't look for DLLs or plugins in folders that those variables or your own PATH name. The rest of that Command Prompt's environment still reaches it, unlike the helper's OpenRGB, which starts with only a short list of system variables. Resize the zone in OpenRGB's window, quit OpenRGB completely rather than to its tray icon, then turn **Enable lighting** back on. That OpenRGB holds an iCUE LINK hub too, out of its own built-in mode, as described above. Before every start, DeadWare also switches off OpenRGB's "SteelSeries Aerox 9 Wireless" detector in those settings, as DeadLight does, because it can stall OpenRGB's device detection while that mouse sleeps; the wired detector stays on. Before every start it also writes OpenRGB's setting for the Corsair iCUE LINK hub, the one that lets OpenRGB find it: off whenever DeadWare has the hub or has given it back after a failed check, so that OpenRGB doesn't take it, and on otherwise. Whenever DeadWare stops, it turns that setting back on, so the OpenRGB that uses DeadWare's settings folder (DeadWare 0.22.0, or one you start with the command above) finds the hub again. An OpenRGB you start in the ordinary way uses its own settings and was never affected. The helper keeps a size-capped log, `devices.log`, at most three files of 2 MiB: in `%ProgramData%\DeadWare\logs\<your user SID>` (`whoami /user` shows your SID), which only administrators can change and only you and administrators can read, when DeadWare runs as administrator, and in `%LOCALAPPDATA%\DeadWare\logs` otherwise. While DeadWare runs as administrator, the helper checks on every start that only administrators can change `%ProgramData%\DeadWare` itself, its `openrgb` and `logs` folders and everything in them, and that programs without administrator rights can't delete the folders above it, such as `C:\ProgramData`, or change their permissions or owner; it checks the rest of `%ProgramData%\DeadWare`, such as the `updates` folder, only on a start where `openrgb` or `logs` doesn't exist yet, such as the first. If one of them fails that check or can't be checked, the helper doesn't start OpenRGB or doesn't keep a log, depending on where the fault is. When it doesn't start OpenRGB, the Lighting page and Settings name the file or folder at fault and the reason, and give the fix where there is one. For `%ProgramData%\DeadWare` or anything in it, remove the file or folder the message says to remove, which needs administrator rights. The message names the file or folder at fault and, for one in the `updates` folder, says to remove `updates` itself. Don't just change its owner or permissions instead: a program without administrator rights may already have changed what's in it. Removing has a cost: DeadWare makes `%ProgramData%\DeadWare` and its `openrgb` and `logs` folders again, but not what was in them, and removing `updates`, alone or with `%ProgramData%\DeadWare`, takes the earlier version kept there with it, so **Roll back & restart** can no longer return to that version. A folder above `%ProgramData%\DeadWare` whose permissions were changed needs its standard permissions back. Then turn lighting off and on. For a link or junction, or a network location, above `%ProgramData%\DeadWare` the message gives no fix: that is how this PC is set up, and DeadWare can't use lighting while it runs as administrator. Without administrator rights the helper uses `%LOCALAPPDATA%\DeadWare` instead, though RAM, motherboard and graphics-card lighting can then be missing, as described above. When DeadWare runs as administrator, the helper also refuses to use `lighting.json` if the path to it goes through a link or junction. If one is there when the helper starts, lighting runs with defaults without saving, and the Lighting page says why; if one appears while the helper runs, each change you make after it fails with "DeadWare couldn't save your lighting settings, so the change wasn't made", and the next start runs with defaults and says why. The helper does the same in rare setups where the path leads somewhere DeadWare can't confirm, such as through a drive letter or network path that points to another folder, except that it notices only when it opens the file: while there's no `lighting.json`, lighting starts normally and each change fails to save. Lighting data is not uploaded.

### Everyday: shortcut, idle and lock

Under the desk on the **Lighting** page, the **Everyday** card ("ways to turn the lights off without opening this page") holds three things. The card is not shown while **Enable lighting** is off in Settings, and it is greyed out while the lighting helper isn't running; the status line at the top of the page says why.

**One switch, three ways to flip it.** The page's **Lights on** switch, the **Turn lights off** / **Turn lights on** line in the tray menu and the shortcut all flip the same saved switch. Lights you turn off this way stay off until you turn them on again, even across a restart of DeadWare or Windows. The tray line follows the saved switch, so it always offers the opposite of what you last chose. It reads **Lights (not available)** and is greyed out only when lighting is off in Settings, or the lighting helper isn't connected or is still starting. When OpenRGB is missing or restarting, or another lighting program is in the way, the line still works and your choice is saved. The shortcut is a Windows global shortcut, so it is meant to work anywhere in Windows, including while DeadWare's window is closed to the tray, because the lighting helper listens for it; that last part has not yet been tried on a real PC, and neither has the shortcut itself from another program. This version adds no new way of reading keys: Windows tells the helper when this one shortcut is pressed, and nothing else about your typing.

**Lights on/off shortcut.** It starts as `Ctrl + Alt + L`, and is claimed from the first start while lighting is on, with no setting to switch on. While DeadWare holds those keys, another program that uses `Ctrl + Alt + L` inside its own window stops receiving them, and DeadWare shows no warning for that. **No shortcut** frees the keys again. The red line below appears only if another program has already claimed the same keys for the whole of Windows. **Change** makes the box read "Press the new keys…" and turns the button into **Cancel** (Esc cancels too). Press the new keys: a letter, a digit, F1 to F24, Space, Insert, Delete, Home, End, Page Up, Page Down, an arrow key or Pause, together with Ctrl, Alt or the Windows key, and Shift too if you like. Other keys, such as punctuation or the number pad, are not accepted and get the same red line. Shift on its own is not enough, and the red line says "Hold Ctrl, Alt or the Windows key together with another key." **No shortcut** removes it, and the box then reads "None". If another program has already claimed those keys, a red line says so ("Another program already uses…") and your earlier shortcut stays as it was.

**Off when the PC sits unused.** The switch starts off. Turn it on and pick how long from the list: 1, 2, 5, 10, 15, 30 or 60 minutes, 10 to start with. Once the PC has had no keyboard or mouse use for that long, the lights go off at once, with no fade, and they come back the moment you touch the mouse or keyboard. DeadWare uses only Windows' own last-input time, how long ago it last saw any input, never what the input was.

**Off when the PC is locked.** The switch starts off. With it on, the lights are meant to go off at the lock screen and come back when you sign back in; that has not yet been tried on a real PC.

**Idle and lock are temporary, and a yellow line says why.** They never change the **Lights on** switch, which stays on. While one of them has the lights dark, a yellow line at the top of the Lighting page says which: that the PC has sat unused for so many minutes, that the PC is locked, or "Waking up… lights return in a few seconds." (after the PC's sleep, below). The desk picture and the keyboard picture show no lights while that line is up, and the grey line under the header reads "lights off" too. You will rarely see the idle line, because touching the mouse or keyboard to look ends the idle spell.

**A press of the shortcut right after an idle spell only brings the lights back.** The shortcut is itself a key press, so it ends an idle spell. A press within about two seconds of an idle spell ending therefore does not turn the **Lights on** switch off; it only returns the lights, which is what you wanted. The page switch and the tray line don't do this: they always set exactly what they say.

**Some lights may stay lit.** A device that runs an effect of its own and has no way to show black, which can be the Lighting Node Pro's front fans, can't be switched off by DeadWare, so it may stay lit when the lights are off. Its card says "Stays lit when lights are off", as it already did for **Lights on**.

### The mouse: battery and sleep

**One card for cable and wireless.** The SteelSeries Aerox 9 has one card, **Mouse · SteelSeries Aerox 9**, whether it is on its cable or on the wireless receiver, and one set of colours and settings for both ("The same colours are used on the cable and wireless."). DeadWare copies the cable mouse's old colours to this card once, at start and when the cable mouse is first listed, if the card has none of its own; the cable's old entry in `lighting.json` stays where it is. After that the two never differ. The line under the heading says how the mouse is connected: "Wireless", "On its cable", "Receiver plugged in · mouse asleep or out of reach" or "Not connected". When it is not connected the mouse is drawn unlit in the desk picture and its card is dimmed, but you can still select it and change its settings.

**Battery.** The **Battery** section shows a bar, a percentage and the charging state. DeadWare reads it while you use the mouse on wireless, at most once a minute, so the reading costs the mouse nothing while it lies still. On the cable it reads every 10 seconds and says whether the mouse is charging. When the mouse is asleep or out of reach, the reading is shown grey as "last known" ("Move the mouse to refresh it."); if it was never read it says "Battery unknown". There is no low-battery warning, and the reading is not saved: it starts again each time DeadWare starts.

**Sleep.** **Mouse sleeps after** sets how long the mouse waits before it goes to sleep: **Never**, or 1, 2, 3, 5, 10, 15 or 20 minutes. It starts on **Leave as the mouse is**, which means DeadWare sends the mouse no sleep time and the line under it says "DeadWare has not changed the mouse's own sleep time." A time you pick is saved as soon as you pick it, and sent to the mouse as soon as it can be. The line under the list tells you where it stands: "Saved and sent to the mouse.", "Saved. Waiting for the mouse." or, on the cable, "Saved. It is sent over the wireless receiver, so it reaches the mouse next time you use it wireless." The time goes to the mouse through the receiver, so it can only be sent while the receiver is plugged in. Choosing **Leave as the mouse is** again only makes DeadWare stop sending a time: it can't put back whatever the mouse had before you chose one.

**Why the lights hold steady while the mouse lies still.** A mouse that keeps being sent moving colours never gets to sleep. So when you have chosen a sleep time (not **Never**, not **Leave as the mouse is**), the time has reached the mouse over the receiver, and the mouse's pointer has stopped moving (on the cable nothing is held), DeadWare stops updating its lights: they hold steady so it can fall asleep and save battery. Moving the mouse brings the effect back. DeadWare tells that the mouse is used only by the pointer moving (any pointer movement counts, from a touchpad or another mouse too), so a click or a scroll on its own does not bring the effect back until the pointer moves too. Turning **Lights on** off darkens the mouse straight away, whatever the sleep time. A mouse that stops answering is left alone: DeadWare sends it nothing until the pointer next moves, then tries at most once a second, so a silent mouse never slows the other lights.

**Plugging in the cable may make all lights blink for a few seconds.** When the mouse's cable arrives and OpenRGB hasn't already found it (a cable already in when DeadWare starts is not an arrival), DeadWare asks OpenRGB to look for hardware again, which is meant to make the cable mouse appear on its cable. OpenRGB does that by dropping and re-adding every device, so all lights may blink for a few seconds. DeadWare asks at most once per cable arrival, and never within a minute of the last time. The colours are sent again once the devices are back. This has not yet been tried with the real mouse.

**When the PC sleeps and wakes.** While Windows is asleep DeadWare sends nothing to any light, not even black. About 10 seconds after the PC wakes it looks at the devices again, sends the lights their colours afresh and turns the mouse's receiver connection (and its sleep time) back on. Until then, while **Lights on** is on, the yellow line reads "Waking up… lights return in a few seconds." and the picture is dark. DeadWare does not itself cause a blink on waking, because it doesn't ask OpenRGB to look for hardware again then; whether the devices come back cleanly, and the wireless mouse itself, have not yet been tried on a real PC.

**Going back.** Settings added in 0.22.0, a changed Everyday card or a mouse sleep time, make the file `lighting.json` version 4. 0.21.0 reads a version-4 file and runs the lights from it, but will not save lighting changes over it; the Everyday settings and sleep time are there again when you update. A PC that never changes the Everyday card or the sleep time keeps a file 0.21.0 can save over, apart from the mouse's colours, now kept under one name. The cable mouse's old colours are still in the file, so 0.21.0 shows them as before.

### The Corsair hub

A Corsair iCUE LINK System Hub lights the fans and pump it carries and, on the same cable, runs their cooling. Until you choose otherwise, OpenRGB lights it, as in 0.22.0. **Settings → Lighting** has, under **OpenRGB location**, a heading **Corsair iCUE LINK hub** with a switch, **DeadWare drives the hub**. With it on, DeadWare lights the hub itself, through its lighting helper, and reads the hub's coolant temperature and its fan and pump speeds. DeadWare never sets fan or pump speeds. Until you turn the switch on, which is how it starts, the hub is lit through OpenRGB and DeadWare doesn't touch it, and the saved lighting file keeps a form 0.22.0 can save over, apart from one thing: in every mode, the hub's colours are copied once under a new name and saved there from then on. The old entry stays in the file, so after going back to 0.22.0 the hub shows its colours from before the update. The switch is greyed out while **Enable lighting** is off or the helper isn't connected.

The line under the switch says where things stand:

- **Off. The hub's lights go through OpenRGB, as they do today.**
- **Switching… the lights blink once.**
- **On. DeadWare is driving the hub.** with the hub's **Coolant**, **Pump** and fan speeds after it, and a line such as "Taken over today at 19:42. Before: pump 2,716 RPM, fans 1,337 · 1,326 · 1,337 RPM." under it. The second line shows only while DeadWare has a reading from before the take-over.
- **On, but DeadWare has let go for now.** with a yellow line that says why (see Letting go below).
- **Off. The hub is on its own.** after DeadWare has given the hub back, with a red-edged box that says why (see Giving the hub back below).
- **On. DeadWare takes the hub in a moment.** while lighting is starting, before the first take of the hub, and while the PC wakes.

**Turning it on.** Click the switch. DeadWare first asks the hub for its coolant temperature and its fan and pump speeds, which changes nothing on it, and opens **Let DeadWare drive the Corsair hub?** The box **Read from the hub just now** shows the **Coolant**, **Pump** and fan numbers it got. If it couldn't read the hub, the box says DeadWare cannot compare speeds afterwards but will still give the hub back if the pump stops. The buttons are **Take over the hub** and **Cancel**, and **Cancel** is the one Enter presses, so the hub is never taken by accident. If you wait more than two minutes before choosing, DeadWare says "That reading was more than two minutes old. Click the switch again." and does nothing. Switching off needs no dialog.

If anything stops the take-over, a red line under the switch says "DeadWare can't take the hub yet:" and lists why, from this list: iCUE is running, the Corsair service is running, DeadLight is running, another OpenRGB is running, no iCUE LINK hub was found, the hub has a part DeadWare doesn't know (with the part's type and model as the hub reported them), the hub has more parts than DeadWare can read, this PC has more than one iCUE LINK hub, lighting is not running, DeadWare can't save its lighting settings. DeadWare refuses a hub with a part it doesn't know rather than guess, and says which. The checks for iCUE, the Corsair services, DeadLight and another OpenRGB are made again just before each take of the hub, so a program that runs only for a moment when you sign in is caught too. If the take-over doesn't finish (iCUE starting, the hub going silent, the PC going to sleep, the lighting settings file being too full to take the result), the red line says "The take-over did not finish" and why, the switch goes back off and the hub's lights stay with OpenRGB. If only writing the result to the lighting file fails (another program has the file locked, say), the take-over still finishes and DeadWare drives the hub until its lighting helper next starts; the file then still says OpenRGB, so the hub goes back to OpenRGB, unless a later lighting change was saved in the meantime.

**What the take-over does.** OpenRGB restarts without the hub, so all the lights blink once; DeadWare then takes the hub and lights it, and OpenRGB carries on with everything else. About 15 seconds later DeadWare reads the speeds again and compares them with exactly the numbers the dialog showed. If the pump or a fan runs more than 10% slower, or can't be read, DeadWare gives the hub back. With no reading in the dialog there is nothing to compare, and DeadWare keeps the hub unless the pump has stopped.

**Giving the hub back.** DeadWare also gives the hub back if, while it drives the hub, the pump reads 0 RPM, or can't be read, for about 10 seconds; the fans are not part of that rule. In both cases the hub is left on its own built-in lights and fan settings, the switch is off, and a box says **DeadWare gave the hub back.**, what happened, and that the hub stays on its own until you choose. Choose **Back to OpenRGB, as before**, which gives the hub's lights back to OpenRGB, or **Try the take-over again**, which does that first, waits until OpenRGB lists the hub (at most 60 seconds, otherwise it says "The hub has not come back through OpenRGB yet. Click the switch when its lights are back."), and then opens the dialog again with a fresh reading. If Settings wasn't open while it waited, nothing opens and no line is shown, even when the hub has come back; click the switch again. Turning the switch on in this state does the same as **Try the take-over again**. To switch off from the **On** state, click the switch: DeadWare gives the hub back, restarts OpenRGB with the hub, and the lights blink once.

**Letting go.** While the switch is on, DeadWare lets go of the hub whenever something else needs it, and the switch stays on. The hub then shows its own built-in lights and fan settings, and DeadWare takes it again by itself when the cause has gone. The Settings line says "DeadWare has let go of the hub because" one of these, and when it takes the hub again:

- iCUE is running, until iCUE has quit;
- the Corsair service is running, until the service has stopped;
- DeadLight is running, until DeadLight has quit;
- another OpenRGB is running, until it has quit;
- lighting has stopped, until lighting runs again;
- no iCUE LINK hub was found, until it is plugged in again;
- this PC has more than one iCUE LINK hub, until only one is plugged in;
- the hub stopped answering, or keeps falling back to its own mode, until DeadWare tries again in a moment;
- the hub has a part DeadWare doesn't know, or more parts than DeadWare can read, until DeadWare is restarted;
- DeadWare can't use the lock Corsair programs share, until DeadWare is restarted;
- OpenRGB still has the hub: DeadWare restarts OpenRGB once without it, and the hub stays let go until that OpenRGB has connected. If OpenRGB lists the hub again after that, the hub stays let go until DeadWare is restarted.

The **Lighting** page says the same in its yellow line, "DeadWare has let go of the Corsair hub because … The hub shows its own built-in effect until …", and its status line says "the Corsair hub is on its own". A hub on its own stays in the device list and in the picture, drawn as "own effect" the way the front fans are, and its settings can still be changed; nothing is painted on it.

**Dark, sleep and wake.** When the lights are turned off, or go off for idle or lock, the hub is painted black and DeadWare keeps hold of it, and the readings carry on. When the PC goes to sleep DeadWare sends the hub nothing at all, not even the hand-back, because the hub loses power or falls back by itself. After waking, DeadWare waits about 10 seconds, then takes the hub again, reading its parts afresh, and paints it; until then the hub shows its own effect.

**Quit, stop and update.** With the switch on, **Quit DeadWare**, **Update & restart**, **Roll back & restart**, turning **Enable lighting** off, choosing another OpenRGB, **Restart as administrator** and a sign-out all hand the hub back first, waiting no longer than 1.5 seconds for it, and only then stop OpenRGB. The hub is then on its own stored lights and fan settings, and stays so until DeadWare takes it again. With the switch off, nothing is handed back, as before. If the helper is ended in Task Manager or hangs, nothing is handed back: the hub should fall back to its own settings after about 10 seconds of silence, which the hardware check is to confirm, and DeadWare takes it again when the helper restarts. If you go back to 0.22.0 and the hub is unlit, see the release note for 0.23.0.

**Readings.** On the **Lighting** page, the hub's card says how it is lit ("lit through OpenRGB", "driven by DeadWare" or "on its own · DeadWare is not lighting it") and has a **Readings** section: **Coolant**, **Pump** and the fans ("Radiator fans" where the desk picture applies, otherwise "Fans"), read from the hub every few seconds. A reading more than 10 seconds old shows as —. With the switch off, the section says readings appear once DeadWare drives the hub, and while the hub is on its own it says there are none. The page's status line counts the hub out of "devices through OpenRGB" while DeadWare drives it or has let go of it.

The Sensors page shows one row per reading, under the hardware "Corsair iCUE LINK hub": **Coolant** in °C, **Pump** in RPM and one row for each fan, named "Radiator fan 1" to "Radiator fan 3" where the desk picture applies and "Fan 1", "Fan 2" and so on otherwise. A hub with three fans and a pump therefore gives five rows. The pump appears twice on a PC whose motherboard also reads it, once from the motherboard and once from the hub, on purpose. The hub's own temperature isn't shown, and the rows are absent, not dashed, while DeadWare isn't driving the hub. Under **Settings → Appearance**, **Show coolant temperature on CPU temperature graphs**, directly under the pump tick box and unticked to start, adds the hub's coolant temperature, dashed and teal by default, to every CPU temperature graph, with a legend line such as "Coolant · 38.5 °C · dashed", a colour dot and a place under **Graph lines**. It is drawn only while DeadWare drives the hub; without a reading the legend says why. Cooling Health doesn't use it.

**The iCUE and DeadLight lines.** Under the switch, **Settings → Lighting** has two more headings. **iCUE** says that iCUE and DeadWare can't both drive the hub and shows three lines, each with a mark: whether iCUE is running (red, with how to quit it), whether the Corsair services are running or start with Windows (red when running, yellow when they only start with Windows, with the steps in Windows Services) and whether iCUE starts when you sign in (yellow, with the steps in Task Manager's Startup apps). Red lines block the take-over; yellow ones never do. On a PC with no trace of iCUE it says "iCUE is not installed on this PC." DeadWare only shows these facts; it never changes iCUE or its services. **DeadLight** shows only when DeadLight is found, with whether it is running and whether its Task Scheduler start-up task is on. While either is not green, **Retire DeadLight** switches off DeadLight's start-up task (it isn't deleted, so you can switch it back on in Task Scheduler), stops DeadLight and the OpenRGB it started, and deletes nothing; it needs DeadWare running as administrator and says so otherwise. If DeadWare can't confirm which folder is DeadLight's, it stops nothing (it still switches off the task, if there is one) and says so, and if the OpenRGB you chose is the one inside DeadLight's folder it leaves that one running. Both headings read their facts at most every 5 seconds while Settings shows them.

**One identity.** However the hub is lit, its colours, tuning and place are saved under one entry. The first time, if that entry has no colours, DeadWare copies them once from the hub's old OpenRGB entry, which stays where it is so that 0.22.0 still finds it. With two or more such hubs listed by OpenRGB, the switch is refused, but the copy is still made, once, from one of the old hub entries, which may not be the hub that stays if you later unplug the other. While DeadWare drives the hub it can't be resized or set to an effect of its own.

**What stays as it is.** DeadWare's hub driver is for the System Hub only. The front three fans stay as they are: on the Lighting Node Pro, set to **Rainbow Wave** as described above.

**Going back to 0.22.0.** While the switch is on, and also after DeadWare has given the hub back (when the switch shows off), `lighting.json` is saved in a newer form (version 5), which 0.22.0 reads and runs the lights from but won't save lighting changes over. Before going back, switch the hub off if it is on, or choose **Back to OpenRGB, as before** if DeadWare gave it back; either saves the file in a form 0.22.0 can save over. Whenever DeadWare stops it turns OpenRGB's setting for the hub back on, but if 0.22.0 shows an unlit hub (the helper was ended, not stopped), start and quit 0.23.0 once.

**Not yet tried on a real PC.** Nothing in this release has been tried on a real PC yet; the owner's hardware check follows. These are not part of that check and are covered by tests only: iCUE starting while DeadWare drives the hub, a failed speed check, the stopped-pump rule, a stuck USB call, Retire with DeadLight running, a hub with unknown parts.

## Network measurements and privacy

The Network chart grows with the window, the application count sits beside or below the search depending on width, and the per-application totals explanation is under **About these totals**.

Interface totals work independently of per-process attribution. Application traffic uses Windows ETW metadata, including TCP/UDP IPv4/IPv6 byte events. Connections optionally saves endpoint metadata locally as described above; recording starts enabled. The Processes page's live per-process data stays in memory. While Per-process monitoring and usage history recording are both on, the busiest apps' image names (never program paths) and their CPU, memory, I/O and GPU are saved for 30 days in `process-history.db`, as Usage history already saves network per app. Adapter descriptions, the hardware names in GPU engine tooltips, are never saved. The program paths of monitored processes are never saved or logged; Open file location and End task read one only when you use them. While a first network use rule exists, alerts.db keeps the upper-case executable names of apps DeadWare has seen use the network, with the first and last minute it saw each, until 400 days after the last, even while Usage and Connections recording are paused; its episodes name the app. Removing the rule stops new names being kept; **Clear history…** for all apps and all time deletes them. Apps in **Don't record these apps** are left out of every saved history, and **Clear history…** removes saved history for one app or all apps ([Usage history](#usage-history)). DeadWare's own program path is stored only where DeadWare needs it: in its **Start with Windows** task while that is on, in an update's handoff files in the `updates` directory, and in the opt-in layout trace. The app never collects packet payloads, URLs, messages or file contents, and does not upload observed endpoints, application names or histories. No firewall management is included.

Rates reflect observed traffic, not ISP billing totals. Adapter totals and attributed application traffic may differ due to virtual adapters, local traffic, protocol overhead or lost events. The combined network graph's last six hours are stored locally; per-application activity and names are not persisted in that graph cache. Connections history is separate, optional and bounded. Thermal and usage history are stored separately as described above. Settings are kept in the user's local application-data directory. Explicit location-database downloads contact DB-IP's download host; update checks/downloads contact GitHub.

Diagnostic output is generated only when explicitly requested. Its process and network data contain no application names or program paths. An error it records can include the exception's message, and the report can include hardware names, drive serial numbers and volume labels; redact those before attaching it to a public issue.

For local troubleshooting, `DeadWare.exe --diagnose output.json --samples 3` collects a short sample and exits. Add `--no-hardware` to isolate Windows counters and network tracking, `--no-etw` to isolate hardware collection from per-app tracing, or `--no-processes` to leave out the process scan and the GPU summary. Diagnostics include provider timings and, unless you pass `--no-processes`, a GPU summary of counts and timings only, whatever the Per-process monitoring setting: GPU counter instances read and skipped, adapters, read milliseconds, the column state and whether the read runs every poll or in its own loop; it names no process or adapter. The process scan and per-app network tracing add no application names or paths, apart from a recorded error's message: each sample gives the number of processes with attributed traffic, not their names. Avoid enabling extended sensors when investigating a responsiveness problem.

For workspace-saving problems, start the app with `--layout-diagnostics "C:\path\layout.jsonl"` using an absolute local output path. This opt-in, size-limited trace records settings paths, open-window IDs and save results; it follows an administrator restart and contains no sensor readings or network traffic. Use a new file or a previous DeadWare layout trace. Treat it as private diagnostic data.

## Build

Install the stable [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) on Windows, then:

```powershell
dotnet build DeadWare.slnx -c Release
dotnet test DeadWare.slnx -c Release
dotnet run --project src/DeadWare.WinUI/DeadWare.WinUI.csproj
```

Create a self-contained portable ZIP and SHA-256 checksum:

```powershell
pwsh -File scripts/publish.ps1 -Version 0.19.0
```

The packaging script runs tests before publishing, bundles the independent self-contained update helper and the self-contained lighting helper, `DeadWare.Devices.exe`, and records all managed file hashes in `deadware-package.json`. Lighting needs `DeadWare.Devices.exe` beside `DeadWare.exe`: the package has it there, but `dotnet run` doesn't. Output goes under `artifacts/`. GitHub Actions runs the same script. Pushing a normal three-part version tag such as `v0.6.0` builds and publishes a normal release after tests pass, using the matching `docs/releases/v0.6.0.md` notes. Workflows use pinned action commits.
